# **Architectural Analysis and ECHO Protocol Integration Specification for Autonomous Knowledge Graphs**

The paradigm of autonomous engineering heavily relies on the capacity of intelligent agents to comprehend the structural
and semantic topology of a codebase. The Egonex-AI project, Understand-Anything, demonstrates the immense utility of
transforming raw repositories into interactive knowledge graphs, converting static files into explorable,
multidimensional representations of business logic and system architecture1. However, integrating such a system into a
deterministic, heavily governed multi-agent harness like Savant Code’s ECHO Protocol v0.2.0 exposes critical
architectural incompatibilities. The reliance on probabilistic Large Language Models (LLMs) for deterministic structural
extraction, the utilization of monolithic processing pipelines, and the dependency on heavyweight web servers for
visualization render the existing Understand-Anything architecture wholly unsuitable for zero-cost, high-velocity
autonomous operations4.
This report provides an exhaustive teardown of the Understand-Anything source architecture and specifies a superior,
purpose-built integration for the ECHO Protocol. By transitioning from a probabilistic JSON-backed pipeline to an
incremental, deterministic SQLite architecture powered by Tree-sitter and the Bun runtime, the proposed design entirely
eliminates LLM token costs associated with graph construction4. Furthermore, this architecture natively enforces the
strict separation of duties mandated by the ECHO Protocol, equipping the Detective, Thinker, and Verifier agents with
sub-millisecond, mathematically verifiable blast-radius analysis without violating their respective tool restrictions4.

## **Source Code and Pipeline Analysis of Understand-Anything**

The Understand-Anything repository, boasting over 77,000 stars and written primarily in TypeScript, operates as a
multi-agent pipeline that scans codebases and constructs a highly faceted knowledge graph1. The core execution flow
relies on sequential data processing, ultimately writing the graph state to JSON files within a local .ua/ directory
before serving it via a Vite web server4.
The primary processing pipeline relies on a sequence of distinct scripts, each responsible for a specific phase of graph
construction. The project scanning phase, executed via scan-project.mjs, is responsible for initial file enumeration
while honoring .gitignore rules to establish the boundaries of the corpus4. Following enumeration, extract-structure.mjs
utilizes Tree-sitter to parse the Abstract Syntax Tree (AST), attempting to isolate structural components such as
functions, classes, and modules4. The relationship mapping phase, driven by extract-import-map.mjs, subsequently maps
import and export relationships to establish foundational edges4. To infer higher-level domains, compute-batches.mjs
applies the Louvain algorithm for community detection4. Finally, merge-batch.mjs consolidates the structural data with
semantic metadata probabilistically generated by an LLM, yielding the final graph payload4.
Despite its modular script design, the data flow and architectural assumptions inherent in this pipeline present severe
limitations when applied to an autonomous context.

| Pipeline Component | Understand-Anything Implementation | Architectural Deficiency in Autonomous Context |
| :---- | :---- | :---- |
| **Parsing Engine** | Tree-sitter augmented by LLM inference | LLMs introduce hallucination risks for deterministic tasks and consume vast token quotas (up to 30 minutes of processing time on mid-sized repositories)4. |
| **Storage Layer** | Flat JSON files in .ua/ directory | In-memory array iteration is required for traversal, precluding granular, index-backed SQL queries by specialized agents4. |
| **Update Mechanism** | Monolithic, full-repository rebuilds | Lacks differential file hashing, resulting in silent staleness where the graph immediately desynchronizes from the repository HEAD after a single commit4. |
| **Visualization** | Vite web server on port 5173 | Creates platform lock-in and heavy runtime dependencies, preventing the generation of portable, offline-ready reports3. |
| **Semantic Extraction** | Dedicated LLM pass per node | Creates an unsustainable financial and computational burden for continuous integration environments4. |

The node schema generated by this pipeline is undeniably comprehensive, encompassing code nodes (file, function, class),
non-code nodes (config, document, endpoint), and knowledge nodes (domain, flow, claim)4. The edges connecting these
nodes—such as imports, calls, depends\_on, and documents—provide a rich tapestry of system behavior4. However, the cost
of generating this topology via LLM-in-the-loop mechanics for problems that are fundamentally deterministic represents a
deep architectural flaw. Autonomous agents require absolute mathematical certainty when navigating call graphs, a
requirement that probabilistic inference inherently violates.

## **Deterministic Extraction and Probabilistic Elimination**

To align with the zero-cost constraint and the requirement for real-time synchronization, the probabilistic elements of
the structural extraction pipeline must be completely eradicated. The foundational principle of the revised architecture
dictates that if a relationship can be proven mathematically via static analysis, it must never be submitted to an LLM
for inference.
The solution relies on deep integration with Tree-sitter, an incremental parsing library capable of generating concrete
syntax trees with extreme speed6. By binding Tree-sitter directly to the Bun runtime—the execution environment of Savant
Code—the system can execute syntax queries locally without network overhead4. Specifically, the tree-sitter-typescript
grammar will be utilized to extract exact node definitions and edge relationships10.
The extraction mechanism leverages Tree-sitter's Query and QueryCursor APIs to execute s-expression matching against the
syntax tree11. To build the baseline topology, the parser will target import\_statement nodes to deterministically
establish IMPORTS edges between file nodes11. Furthermore, call\_expression, function\_declaration, and
method\_definition nodes will be captured to construct precise CALLS edges between distinct symbol nodes12. Because this
process operates entirely on the local AST, the resulting call graph is mathematically absolute, eliminating the
hallucination vectors present in the Understand-Anything architecture. This deterministic extraction operates at
sub-millisecond latencies, fundamentally shifting graph generation from a costly batch process to an ambient, real-time
computational service.

## **Incremental Update Strategy and Cache Invalidation**

Monolithic processing pipelines are antithetical to the Perfection Loop of the ECHO Protocol. Agents constantly iterate
on code during the GREEN (Forge) and AUDIT (Verifier) phases4. If the knowledge graph requires a full rebuild to reflect
these changes, the latency renders the graph useless for continuous validation. Therefore, the architecture must support
differential, incremental updates.
The incremental update strategy relies on a robust hashing and cache invalidation mechanism. During the project scanning
phase, every file enumerated in the repository will be hashed using an ultra-fast, non-cryptographic hashing algorithm,
specifically XXH3. The resulting hash will be stored in the graph database alongside the file's primary record.
Upon any subsequent trigger of the graph extraction service, the system will perform a rapid differential check. The
scanner will compute the XXH3 hash of the current file state on disk and compare it against the stored hash in the
database. Only files exhibiting a hash mismatch will be flagged for Tree-sitter AST parsing.
This differential approach introduces necessary complexities regarding edge invalidation. When a file is modified, all
existing nodes (functions, classes) and edges (imports, calls) originating from that specific file must be
systematically pruned from the database before the new AST is parsed and inserted. The relational database schema will
utilize cascading deletes to ensure that removing a stale file node instantly eradicates all dependent topological data,
preventing the accumulation of orphaned nodes. If a file is deleted entirely from the repository, the staleness
detection mechanism will identify the missing file path, triggering a cascading delete that cleans the graph perfectly
without requiring a full rebuild.

## **ECHO Protocol Integration and Separation of Duties**

The ECHO Protocol v0.2.0 operates as a strict engineering governance framework, organizing a 10-agent roster around a
non-negotiable separation of duties4. The integration of the knowledge graph must respect these boundaries absolutely.
No agent may possess tools that violate their defined phase constraints.
Under the ECHO Protocol, the Orchestrator serves as the primary router and hybrid coder, possessing write tools like
write\_file and str\_replace, but lacking verification tools like bash4. The Detective operates in the RED phase,
restricted entirely to read-only codebase analysis4. The Forge operates in the GREEN phase, possessing write
capabilities but barred from verification4. Crucially, the Verifier owns the AUDIT phase, tasked with double-auditing
code without any write tools whatsoever4.
Because no single agent is permitted to both write code and verify it, the construction of the knowledge graph cannot be
owned by any conversational agent. If the Forge builds the graph and subsequently uses it to verify its own
implementation, the core tenet of the Double Audit is violated4.
Therefore, graph construction must be implemented as an ambient infrastructure service—a localized daemon operating
invisibly alongside the bash and database infrastructure helpers4. The agents will interact with the graph exclusively
through specialized, read-only Model Context Protocol (MCP) tools.

| Agent Role | FSM Phase | Tool Access | Graph Utilization Strategy |
| :---- | :---- | :---- | :---- |
| **Orchestrator** | ALL | query\_domain | Routes complex tasks by analyzing which domain clusters (via Louvain output) are affected by a prompt, determining if FID-bound delegation is required. |
| **Detective** | RED | query\_blast\_radius | Identifies downstream dependencies of a bug. Validates Law 1 (Read 0-EOF) by ensuring all tightly coupled files are pulled into context prior to modifications. |
| **Thinker** | Planning | query\_architecture | Ingests structural relationships during sequentialthinking to evaluate proposed refactors, ensuring the design does not violate existing bounded contexts. |
| **Verifier** | AUDIT | verify\_reachability | Replaces probabilistic text grepping with mathematical CTE traversal to definitively prove that a newly implemented function is reachable from a production entry point (Law 4). |
| **Scout** | Explore | query\_node\_edges | Navigates the graph interactively to gather deep context on unfamiliar codebases without consuming massive LLM tokens reading raw source files. |

## **The Perfection Loop and Immutable Laws**

The Perfection Loop is a Finite State Machine (idle → red → green → audit → complete) that governs the lifecycle of a
Feature Implementation Document (FID)4. The integration of the deterministic knowledge graph fundamentally enhances the
mathematical rigor of this loop.
During the RED phase, the Detective agent catalogues all failures and issues4. By leveraging the query\_blast\_radius
MCP tool, the Detective can instantly generate a definitive list of all files that import a failing module, ensuring the
scope of the FID is exhaustive. Moving into the GREEN phase, the Thinker and Recorder agents design the fix4. The
Thinker utilizes the graph to verify that its proposed solution adheres to the existing architectural patterns,
minimizing structural entropy.
The most profound impact of the graph occurs during the AUDIT phase, specifically regarding the enforcement of Law 4:
Verify Call-Graph Reachability4. The ECHO Protocol dictates that after wiring any feature, the agent must confirm it is
actively called by a production entry point, noting that compilation is not synonymous with verification4. Historically,
this required the Verifier to execute highly error-prone grep commands, which struggle with dynamic dispatch, aliased
imports, and deeply nested callbacks.
With the SQLite-backed knowledge graph, the Verifier agent will execute a recursive graph traversal. By querying the
database, the Verifier can trace a mathematical path from the newly forged function back through the CALLS edges until
it intersects with a known root node (e.g., an Express route handler or an exported public API). If the traversal yields
zero paths, the Verifier deterministically fails the AUDIT phase, forcing the system into the SELF-CORRECT state4. This
transforms Law 4 from a heuristic check into an absolute mathematical proof.
Finally, in the COMPLETE phase, the Recorder agent will query a localized snapshot of the modified graph cluster. This
subgraph representation will be embedded directly into the archived FID and the CHANGELOG.md entry, providing permanent,
structural context regarding the historical evolution of the codebase4.

## **Storage Architecture: SQLite and Recursive Graph Traversal**

Understand-Anything's reliance on flat JSON files stored in a .ua/ directory introduces severe read-latency
bottlenecks4. To traverse a deep call graph using JSON, the entire payload must be deserialized into memory, and
recursive pathfinding must be executed via application-level array iteration. This memory-bound approach is unscalable
and introduces unacceptable latency for agentic workflows.
The optimal storage architecture for the Savant integration leverages a local SQLite database, executed via Bun's native
bun:sqlite driver1. SQLite provides absolute ACID compliance, robust indexing, and advanced query capabilities without
requiring a dedicated background server process.
To maximize throughput and eliminate read/write lock contention between the background AST parser and the conversational
agents, the SQLite connection must be initialized in Write-Ahead Logging (WAL) mode13. Executing PRAGMA journal\_mode \=
WAL; allows simultaneous readers and writers; the AST extractor can write new nodes to the \-wal file while the Thinker
agent simultaneously queries the \-shm shared-memory index, ensuring zero blocking during autonomous operation14.

### **Relational Schema Design**

The knowledge graph will be modeled using a highly normalized relational schema designed specifically to optimize
recursive traversal and differential updates.

| Table Name | Column | Data Type | Constraints and Relational Mechanics |
| :---- | :---- | :---- | :---- |
| files | id | INTEGER | PRIMARY KEY |
|  | path | TEXT | UNIQUE, indexed for rapid Scout lookups |
|  | hash | TEXT | XXH3 hash for incremental differential invalidation |
| nodes | id | INTEGER | PRIMARY KEY |
|  | file\_id | INTEGER | FOREIGN KEY (files.id) ON DELETE CASCADE |
|  | type | TEXT | AST classification (e.g., 'class', 'function', 'interface') |
|  | name | TEXT | Symbol identifier extracted via Tree-sitter |
|  | cluster\_id | INTEGER | Bounded context identifier assigned by Louvain algorithm |
| edges | source\_id | INTEGER | FOREIGN KEY (nodes.id) ON DELETE CASCADE |
|  | target\_id | INTEGER | FOREIGN KEY (nodes.id) ON DELETE CASCADE |
|  | type | TEXT | Relationship classification ('CALLS', 'IMPORTS', 'EXTENDS') |

### **Recursive Common Table Expressions (CTEs)**

The true power of migrating to SQLite lies in the ability to execute recursive Common Table Expressions (CTEs) via the
WITH RECURSIVE syntax16. A recursive CTE acts as a temporary view that evaluates in a loop, allowing the database engine
to traverse arbitrary-depth trees and graphs natively without application-level logic16.
Every recursive CTE consists of two distinct queries joined by a UNION ALL operator: the anchor member and the recursive
member19. The anchor member executes once to establish the starting nodes, adding them to a conceptual queue. The
recursive member then executes repeatedly, joining the base tables against the rows generated in the previous iteration,
adding newly discovered nodes to the queue until no further relationships are found16.
This mechanism is explicitly how the Verifier agent will enforce Law 4\. To calculate reachability, the Verifier will
execute a query similar to the following:

SQL  
WITH RECURSIVE call\_path(node\_id, path, depth) AS (  
    \-- Anchor Member: Initialize traversal at the target function  
    SELECT id, ',' || id || ',', 0   
    FROM nodes WHERE name \= 'newFeatureFunction'  

    UNION ALL  

    \-- Recursive Member: Traverse backwards along upstream 'CALLS' edges  
    SELECT e.source\_id, cp.path || e.source\_id || ',', cp.depth \+ 1  
    FROM edges e  
    JOIN call\_path cp ON e.target\_id \= cp.node\_id  
    WHERE e.type \= 'CALLS'  
    \-- Cycle Detection: Prevent infinite recursion in cyclic graphs  
    AND instr(cp.path, ',' || e.source\_id || ',') \= 0  
    AND cp.depth \< 50  
)  
SELECT n.name, n.type   
FROM call\_path cp  
JOIN nodes n ON cp.node\_id \= n.id;

A critical architectural consideration when traversing code graphs is the inevitability of cycles (e.g., mutually
recursive functions)20. If a recursive CTE encounters a cycle without a termination condition, it will loop infinitely
until database memory is exhausted18. Modern implementations of PostgreSQL (version 14+) mitigate this natively via the
CYCLE keyword, which automatically tracks visited nodes22. However, SQLite lacks native cycle detection syntax22.
To prevent infinite loops in SQLite, the architecture must implement manual cycle detection. As demonstrated in the
query above, this is achieved by accumulating a comma-delimited string representing the traversal path (e.g.,
,14,42,89,)23. During each iteration of the recursive member, the instr() function checks if the target node's ID
already exists within the accumulated path string24. If the node is found, the recursion branch is immediately
terminated, ensuring safe, depth-limited traversal across complex, cyclic codebases20.

## **Algorithmic Domain Clustering**

While structural extraction (functions, classes, imports) is deterministic, grouping those structural elements into
distinct semantic "domains" or "business logic" clusters requires higher-order analysis. Understand-Anything relies
heavily on LLM inference to draw these boundaries, contributing significantly to its massive token consumption4. To
eliminate this cost, the proposed architecture replaces LLM semantic mapping with deterministic, algorithmic community
detection.
The integration will utilize graphology-communities-louvain, an open-source, TypeScript-native implementation of the
Louvain modularity optimization algorithm25. The Louvain algorithm detects communities in dense networks by iteratively
reassigning nodes to adjacent communities if the move results in a higher overall modularity score for the graph25. This
algorithm is highly efficient and capable of operating natively within the Bun runtime directly over the structural
edges extracted by Tree-sitter28.
To ensure the algorithmic clusters accurately represent human-readable bounded contexts (e.g., separating an
Authentication domain from a Billing domain), two specific tuning mechanisms will be employed:

> 1. **Resolution Parameter Scaling**: The Louvain implementation accepts a resolution parameter, which controls the
> 1. density of the resulting clusters26. A higher resolution forces the algorithm to generate a large number of tightly
> 1. packed, granular communities, while a lower resolution encourages broader, monolithic clusters26. The system will
> 1. dynamically scale this resolution parameter inversely proportional to the total node count of the repository,
> 1. preventing massive codebases from devolving into overly fragmented micro-clusters.
> 2. **Deterministic Edge Weighting**: Modularity algorithms respond strongly to edge weights28. By deterministically
> 2. assigning weights during the Tree-sitter extraction phase, the system can coax the Louvain algorithm into
> 2. respecting architectural boundaries. IMPORTS edges will carry a baseline weight of 1.0. CALLS edges will carry a
> 2. weight of 2.0, reflecting tighter coupling. Crucially, cross-directory dependencies will incur a fractional weight
> 2. penalty, naturally encouraging the algorithm to draw domain boundaries around existing filesystem directories
> 2. without requiring any LLM comprehension26.

Once computed, the resulting community ID will be written directly to the cluster\_id column in the SQLite nodes table,
granting the Thinker and Orchestrator agents immediate access to probabilistically accurate domain boundaries using
strict mathematical graph theory.

## **Token Optimization and Ambient Semantic Labeling**

While algorithmic clustering solves the boundary problem, the graph still requires semantic labels (e.g., naming Cluster
4 the "Payment Processing Pipeline") to be truly useful to autonomous agents. Executing a dedicated LLM pass across the
entire repository to generate these labels, as seen in Understand-Anything, is financially unviable. The ECHO
integration will solve this via Ambient Semantic Labeling and in-band data collection.
Rather than dedicating a separate model call to graph labeling, semantic metadata will be gathered implicitly during the
natural execution of the ECHO protocol.
During the RED phase, the Detective agent routinely reads files and subtrees to analyze issues4. The Detective's system
prompt will be augmented with a lightweight structured output tool, compelling the agent to yield a concise, 10-word
semantic description of the file's primary business logic alongside its standard bug analysis.
Similarly, during Hybrid Execution, the Orchestrator deeply understands the context of the files it modifies. The
standard write\_file and apply\_patch tools will be extended to accept an optional semantic\_update parameter4. The
Scribe agent, already responsible for generating session summaries and synthesizing knowledge capture, will aggregate
these ambient observations and asynchronously execute UPDATE statements against the SQLite nodes table4. This mechanism
allows the graph's semantic richness to grow organically over time at precisely zero additional token cost.
Furthermore, when agents query the graph, returning raw JSON arrays representing hundreds of edges rapidly exhausts
context windows. The MCP tools exposing the SQLite database will implement "Caveman" prompt compression techniques5. The
relational data will be flattened into dense, syntax-light representations—for example, converting verbose JSON objects
into streamlined text strings like AuthService \-\> \[calls\] \-\> TokenValidator (Cluster 3). This structured output
minimizes wasted tokens while preserving complete topological awareness for the Thinker agent.

## **Visualization and Portable HTML Export**

Understand-Anything requires users to spin up a Vite web server on port 5173 to render the interactive dashboard3. In
automated, agentic environments, relying on persistent local web servers introduces brittle networking dependencies and
platform lock-in. Furthermore, it prevents the seamless sharing of graph reports in restricted environments or via
email.
To align with Savant Code's existing capabilities, specifically the /export command which writes branded, self-contained
HTML reports, the knowledge graph visualization will be completely decoupled from Node.js and Vite4.
The visualization layer will be rebuilt utilizing Cytoscape.js, a mature, highly optimized graph theory library
distributed under the MIT license30. Cytoscape.js is designed for massive network rendering utilizing HTML5 Canvas,
providing out-of-the-box support for panning, zooming, and complex layouts like D3 and Dagre30. Crucially, Cytoscape.js
has zero external dependencies and supports execution in legacy ES5 browser environments30.
Upon invocation of the /export command, the Savant CLI will query the SQLite database, serialize the entire structural
and semantic graph into a Cytoscape-compatible JSON object, and inject this payload inline into a \<script\> tag within
a static HTML template33. The Cytoscape.js library itself will be inlined or loaded via a fallback CDN32.
The resulting artifact is a single, heavily optimized HTML file that contains the entire explorable graph. This file
requires zero backend infrastructure, can be viewed offline, and can be autonomously archived by the Recorder agent into
the dev/fids/archive/ directory at the conclusion of the COMPLETE phase4. The interactive interface will feature fuzzy
searching across node names and cluster IDs, bidirectional shortest-path finding between microservices, and color-coding
dictated by the algorithmic Louvain clusters3.

To contextualize the superiority of this integration, it must be evaluated against existing paradigms, namely the
incumbent Understand-Anything architecture and generalized graph database solutions (such as Engraphis or Neo4j
deployments).

| **Parsing Engine** | Probabilistic LLM \+ Tree-sitter | Generic textual or AST parsers | Pure Deterministic Tree-sitter via Bun |
| **Storage Architecture** | JSON Files in .ua/ | JVM-backed Server / Heavy Daemons | Embedded SQLite (WAL mode, ACID) |

The native integration eliminates the primary failure vectors of Understand-Anything: the hallucination risk inherent in

output. Compared to heavy external graph databases like Engraphis, the embedded SQLite approach ensures that the agent
harness remains self-contained, portable, and executes with local, zero-network latency.

## **Feature Specification and Phased Implementation Strategy**

The implementation of this architecture will be executed in a phased, dependency-aware sequence to ensure the core ECHO
Protocol operations remain uninterrupted during deployment.

### **Phase 1: Deterministic Storage and Parsing Infrastructure**

The foundational layer establishes the data schema and extraction mechanisms without agent interaction.

* Initialize the Bun SQLite database connection, explicitly setting PRAGMA journal\_mode \= WAL; and defining the
* normalized files, nodes, and edges tables with cascading foreign keys.
* Integrate tree-sitter-typescript C bindings into the Bun environment.  
* Develop the s-expression queries to accurately capture import\_statement (file edges) and call\_expression /
* method\_definition (symbol edges).
* Implement the XXH3 hashing pipeline to enable the incremental, differential parsing engine, ensuring stale nodes are
* pruned upon hash mismatch.

### **Phase 2: Algorithmic Augmentation**

This phase introduces semantic grouping without LLM reliance.

* Integrate the graphology and graphology-communities-louvain libraries into the runtime.  
* Establish the dynamic resolution parameter scaling logic based on absolute node counts.  
* Implement the deterministic edge weighting algorithm (prioritizing CALLS over cross-directory IMPORTS).  
* Map the resulting Louvain community IDs back into the SQLite nodes table for rapid querying.

### **Phase 3: ECHO Protocol Tooling and Ambient Labeling**

This phase exposes the graph to the autonomous agents while strictly maintaining the separation of duties.

* Develop read-only MCP tools for the Scout (query\_graph\_blast\_radius) and Thinker (query\_domain\_boundaries)
* agents, implementing "Caveman" prompt compression for optimized token usage.
* Develop the verify\_call\_reachability tool for the Verifier agent. This tool will execute the recursive CTE with
* manual cycle detection (instr(path)) to mathematically prove Law 4 compliance.
* Extend the Orchestrator (write\_file, apply\_patch), Detective, and Scribe prompts to support ambient, in-band
* semantic labeling, gradually populating the graph's metadata.

### **Phase 4: Portable Presentation Layer**

The final phase focuses on human-in-the-loop visualization and archival capabilities.

* Develop the standalone HTML template utilizing Cytoscape.js and the D3 Dagre layout engine.  
* Implement the /export CLI command to serialize the SQLite payload into JSON and inject it inline into the HTML
* artifact.
* Build the frontend interactive components, including fuzzy node search, shortest-path calculation, and cluster-based
* color coding, ensuring full functionality in an offline state.

By executing this specification, the Savant Code ecosystem will absorb the profound benefits of a deep knowledge graph
while completely bypassing the financial, operational, and probabilistic limitations of existing monolithic
implementations. The resulting architecture ensures that engineering governance is enforced not just by prompted
guidelines, but by uncompromising, mathematical reality.
