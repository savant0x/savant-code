# **Architectural Blueprint for Savant-Code "Auto Drive": Autonomous End-to-End Execution**

## **The Paradigmatic Shift to Goal-Driven Autonomy**

The evolution of multi-agent coding harnesses has rapidly progressed from interactive, prompt-driven assistants to highly autonomous execution engines capable of transforming abstract objectives into production-ready software. This architectural blueprint outlines the integration of an "Auto Drive" system within the Savant-Code framework, a governed TypeScript/Bun terminal agent harness defined by its strict adherence to the ECHO Protocol v0.2.01. The primary objective of this integration is to enable an operator to provide a singular, high-level end goal—such as the creation of a social network or the implementation of a complex authentication module—and allow the harness to autonomously decompose the objective, plan the architecture, execute the implementation, verify the resulting code, and ship the final product without intermediate human intervention1.  
The Savant-Code environment currently enforces mechanical quality through a rigid 15-Law system via the ECHO Harness Enforcement Layer (EHEL) and a multi-phase Perfection Loop Finite State Machine (FSM)1. Every code modification is bound to a Feature Implementation Document (FID) lifecycle, ensuring strict separation of duties among a roster of ten specialized agents2. To achieve fully autonomous execution without compromising this stringent governance, the architecture must draw critical inspiration from the Every Code ecosystem1. Every Code, a highly developed fork of the OpenAI Codex CLI, pioneered the implementation of decoupled background reviews, termed "ghost-commits," alongside sophisticated long-session stability patterns governed by bounded state maps1. By synthesizing the immutable governance of Savant-Code with the fluid, autonomous orchestration patterns of Every Code, the resulting Auto Drive system will establish a localized, Bring-Your-Own-Key (BYOK) environment capable of sustained, high-complexity software engineering1.

## **Core Architecture: Auto Drive Orchestration Layer**

The integration of Auto Drive into Savant-Code requires a foundational architectural decision: Auto Drive must not function as a new, independent agent within the ten-agent roster, nor should it replace the existing ECHO Protocol. Instead, Auto Drive is designed as an autonomous continuation driver operating entirely within the Orchestrator agent's execution modality, effectively extending the existing Durable Goal Engine introduced in recent harness iterations1. The system acts as a perpetual loop layered directly on top of the Perfection Loop FSM, consuming FIDs and mechanically triggering phase transitions that would normally require operator input.  
The Orchestrator within Savant-Code currently manages work routing, protocol enforcement, and the instantiation of sub-agents2. By default, the Orchestrator halts execution at the conclusion of a discrete task, returning control to the terminal UI (OpenTUI) to await operator confirmation3. The Auto Drive layer intercepts these termination states. When the operator initializes the system using the /auto "end goal" command, the Auto Drive continuation driver initializes a macro-state within the TUI's Zustand store, tracking the overarching objective as an immutable \<untrusted\_objective\> payload7.  
To understand how Auto Drive fundamentally alters the execution flow while preserving governance, a comparison of the operational states is necessary.

| Execution Layer | Standard Savant-Code Behavior | Auto Drive Orchestration Behavior |
| :---- | :---- | :---- |
| **Phase Transition** | Operator manually approves movement from GREEN to AUDIT3. | Continuation driver intercepts completion hooks and programmatically invokes the transition\_phase tool2. |
| **Queue Management** | FIDs are tracked in the sidebar; the user dictates which FID to process3. | Auto Drive mechanically parses dev/fids/ and processes documents sequentially based on creation ID2. |
| **Error Recovery** | Verification failures return to the TUI; the user must instruct the agent to fix the issue3. | Driver captures EHEL rejection exit codes, transitions the FSM to SELF\_CORRECT, and loops back without user input1. |
| **Completion** | Session ends when the current FID is marked closed3. | Session evaluates the entire dev/fids/ directory, concluding only when the open FID count reaches zero1. |

The Auto Drive state machine operates continuously, managing the lifecycle of the underlying Perfection Loop. It leverages the existing AgentActivity indicators (such as idle, thinking, tool, subagent, and researching) to broadcast its current operational status to the OpenTUI sidebar, ensuring the operator maintains complete observational awareness of the autonomous process despite the absence of required input8.

## **The Decomposition Engine: Translating Abstract Goals**

A fundamental challenge in autonomous engineering is bridging the semantic gap between a generalized user command and the highly specific, isolated file modifications required to execute it safely. Attempting to implement a broad directive directly violates ECHO Law 1 (Read 0-EOF Before Touch) and Law 2 (Present Before Act)3. The Auto Drive architecture resolves this through the Decomposition Engine, an automated sequence executed immediately upon session initialization, utilizing the Thinker, Detective, and Recorder agents to generate a structured backlog.  
The sequence begins with the Orchestrator spawning the Thinker agent. The Thinker is strictly mandated to utilize the sequentialthinking tool for all non-trivial reasoning2. The tool schema requires the agent to accumulate stacked reasoning steps, capturing thoughts, revisions, and branching alternatives before converging on a final architectural strategy2. The Thinker parses the operator's one-sentence goal and utilizes this sequential logic to define constraints, identify necessary modules, and break the objective into a series of logical implementation phases.  
Once the conceptual milestones are established, they must be grounded in the physical reality of the existing repository. The Orchestrator subsequently spawns the Detective agent. The Detective interfaces with the packages/knowledge-graph engine, a deterministic, SQLite-backed codebase indexer built on tree-sitter parsing2. The Detective utilizes native read-only tools, specifically query\_blast\_radius, query\_node\_edges, and query\_domain\_clusters, to map the Thinker's conceptual milestones to exact file paths and system architectures2. This ensures the agent accurately assesses the existing codebase infrastructure before generating specifications.  
The final stage of the decomposition process relies on the Recorder agent. The Recorder is the sole entity permitted to manipulate the Feature Implementation Document lifecycle2. Receiving the mapped objectives from the Thinker and Detective, the Recorder utilizes the write\_file tool to generate a series of individual FIDs within the dev/fids/ directory2. Each document is formatted strictly as FID-YYYY-MMDD-NNN-{title}.md and initialized with the status created2. The generation of these documents constitutes the creation of the Auto Drive backlog, transforming an insurmountable global goal into a mechanical queue of highly controlled, isolated tasks.

## **Phase Execution and Mechanical Quality Enforcement**

With the backlog established in the dev/fids/ directory, Auto Drive initiates the execution phase. The system selects the first created FID and forces it through the Perfection Loop FSM, ensuring that quality rules are enforced mechanically at the tool-executor level without relying on the agent's internal compliance1. The progression through the states—RED, GREEN, AUDIT, ADVERSARIAL, and COMPLETE—must occur systematically for every individual document.  
The execution begins in the RED Phase. Auto Drive instructs the Detective to conduct a deep analysis of the specific FID's scope, mapping call-graph reachability and cataloging evidence of required changes directly into the document3. Once this analysis is recorded, the continuation driver forces a transition to the GREEN Phase, wherein the Thinker and Recorder collaborate to document the proposed fix3. The Thinker must define the exact implementation strategy with minimal changes, selecting the most robust defaults to ensure no architectural questions remain unanswered within the FID3.  
The architecture's reliance on mechanical governance becomes critical during the AUDIT and ADVERSARIAL phases. When Auto Drive transitions the FSM to AUDIT, the Verifier agent is instantiated. In accordance with the separation of duties mandated by the ECHO Protocol, the Verifier possesses absolutely zero tools; it cannot execute code, run tests, or modify files2. Instead, the ECHO Harness Enforcement Layer (EHEL) mechanically runs the project's build, test, and lint commands, injecting the resulting stdout and stderr payloads directly into the Verifier's message history3. The Verifier evaluates this injected evidence, providing a double-audit of the proposed solution and citing specific file:line references for every PASS or FAIL determination2.  
Following the Verifier, the system enters the ADVERSARIAL Phase. The Adversary agent conducts a read-only meta-verification of the Verifier's output2. It is tasked with refuting unevidenced PASS claims, re-auditing FAIL decisions, and resolving missing citations2. The Adversary's verdict overrides the Verifier, ensuring that hallucinated test results or superficial approvals are mechanically blocked before any code is modified2.  
If the FID achieves a clean verdict through both audit layers, it reaches the converged status, unlocking the IMPLEMENTATION Phase1. Auto Drive spawns the Forge agent, the only entity permitted to utilize write\_file and str\_replace for actual codebase modifications2. As Forge implements the code, the Zero-Trust Agentic Provenance (ZTAP) subsystem engages, recording hash-only, per-role Ed25519-signed write receipts into an append-only session ledger, proving cryptographic custody of every automated modification7. Post-implementation, the Verifier is called a final time to validate the physical code against the converged FID. Upon a successful final verification, the Recorder updates the FID status to closed, archives the document, and appends the modifications to the project's CHANGELOG.md2.

## **Autonomous Self-Healing and FSM Feedback Loops**

The primary distinction between standard agent execution and a fully realized Auto Drive system is the capacity for autonomous self-healing. When verification fails, the system must not halt and await human debugging; it must autonomously route the failure back into the logic engine1. Within Savant-Code, this is achieved by leveraging the FSM's SELF\_CORRECT state and integrating it tightly with the Auto Drive continuation driver1.  
Self-healing mechanisms are triggered under several distinct conditions during the execution pipeline.

| Failure Origin | Detection Mechanism | Auto Drive Routing Action |
| :---- | :---- | :---- |
| **Audit Rejection** | Verifier issues a FAIL based on EHEL-injected test results during the AUDIT phase2. | Driver transitions FSM to SELF\_CORRECT. Thinker and Recorder update the GREEN section of the FID; FSM loops back to AUDIT3. |
| **Adversarial Refutation** | Adversary detects an unevidenced PASS or invalid citation during the ADVERSARIAL phase2. | Driver overrides the Verifier's approval, forces a transition to SELF\_CORRECT, and demands a revised implementation plan3. |
| **Implementation Error** | Forge produces syntactically incorrect code, tripping the EHEL post-write scanner (e.g., ESLint or typecheck failure)3. | EHEL blocks the completion. Driver packages the stderr exit code into an error-correction prompt and forces Forge to retry the implementation. |
| **Protocol Violation** | Forge attempts to write a file without reading it first, violating ECHO Law 13. | EHEL blocks the tool call via beforeToolCall gate7. Driver intercepts the failure and forces a file read before permitting the write. |

To prevent the autonomous system from entering infinite loops during complex debugging scenarios, Auto Drive relies heavily on the per-session circuit breakers maintained within the AgentState architecture2. The charChangeTotal limit ensures that no single pass exceeds a ten percent Levenshtein character modification threshold, preventing the agent from rewriting entire architectures in a panic2. The iterationCount enforces a hard stop after ten maximum iterations per FID2. Most crucially, the oscillationDetections mechanism tracks the lastIssueIds array; if the system attempts to fix the exact same issue three times without success, the circuit breaker trips2. When a circuit breaker engages, Auto Drive immediately suspends the FSM, alters the global status to blocked, and halts execution to await human intervention, ensuring the safety and integrity of the repository.

## **Bounded State Mechanics for Long-Session Stability**

Executing an end-to-end objective autonomously over several hours invariably challenges the context window limitations of underlying Large Language Models. As Auto Drive processes sequential FIDs, the accretion of tool outputs, historical thinking patterns, and diffs can precipitate context collapse, resulting in degraded reasoning and hallucinated syntax. To guarantee long-session stability, the Auto Drive architecture implements bounded state mechanics directly inspired by the Every Code ecosystem, which utilizes hard caps on core state maps and deterministic drop/trim behaviors to maintain context hygiene1.  
Savant-Code currently features a four-layer progressive auto-compaction system, which Auto Drive elevates from a reactive mechanism to a proactive, deterministic lifecycle event executed at the boundary of every FID closure7.  
The first layer (L0) engages the Scribe agent to summarize older conversation turns, stripping conversational verbosity while retaining architectural decisions7. The second layer (L1) performs immediate tool compression; massive raw outputs generated by list\_directory or read\_files are algorithmically truncated. Once a file is processed and no longer actively required for the current FID, its physical content is purged from the context window and replaced with a structural summary placeholder7. The third layer (L2) utilizes the dedicated context-pruner helper agent to aggressively drop stale reasoning context, specifically targeting and eliminating the Thinker's lengthy sequentialthinking chains from prior, already-closed FIDs2. The final layer (L3) acts as an emergency reduction protocol; if the context approaches critical thresholds despite previous compactions, the driver pauses the FSM, serializes the entire session memory to the dev/scratchpad/ directory, and reinitializes the Orchestrator utilizing only the original global\_goal, the currently active FID, and a highly condensed SCOPE.md artifact3.  
Beyond LLM context limits, the underlying TUI and Node.js/Bun runtimes must also be protected from memory leaks during multi-hour autonomous sessions. Emulating Every Code's coordinator boundaries, the Savant-Code Auto Drive blueprint mandates hard caps on the TUI's prompt, agent, and runtime state caches4. Utilizing the Immer library within the Zustand store, arrays such as thoughtHistory are destructively trimmed to retain only a bounded maximum of recent entries, ensuring deterministic stop control and preventing memory ballooning2.

## **Background Auto Review via Ghost-Commit Watchers**

A defining feature of the Every Code architecture is "Auto Review," a background ghost-commit watcher that executes code quality reviews in a separate worktree whenever code is modified, reporting issues and patches without blocking the main operational thread1. Integrating a comparable, non-blocking background review mechanism into Savant-Code enhances mechanical quality enforcement by providing continuous oversight during Auto Drive's implementation phases.  
Because Savant-Code operates fundamentally on a single-agent/single-model paradigm1, the Auto Review system relies on physical process isolation rather than simultaneous multi-model API requests. The architecture leverages Bun's native Worker threads to instantiate a headless, parallel version of the Savant-Code runtime.  
The background review lifecycle is triggered mechanically. When the Forge agent completes an implementation pass and the target files are modified, the EHEL framework fires a project-scoped PostToolUse lifecycle hook7. The Auto Drive system intercepts this hook and initiates the background process. First, the system creates a lightweight Git worktree—or a highly optimized file-system copy—within a hidden operational directory (.savant/worktrees/ghost-review/)4. Second, a background Bun worker is spawned, executing a dedicated review agent within the isolated context of this new worktree. This allows the primary Auto Drive thread to seamlessly continue its FSM progression, advancing to the next logical task without stalling the OpenTUI interface1.  
The background review agent evaluates the Forge implementations against ECHO Law 4 (call-graph reachability) and Law 6 (strict type safety)3. If the review detects anomalies, anti-patterns, or logic errors, it generates ready-to-apply diffs and patches. Crucially, these patches are not immediately injected into the active context, which would cause disruptive task-injection4. Instead, the background worker emits a compliance\_warning receipt7. This receipt is appended to a bounded update queue maintained within the main Orchestrator's state.  
At the commencement of the next FSM phase, the Thinker agent is instructed to read this non-blocking history-visible queue4. If actionable background patches exist, the Thinker processes them as newly discovered incoming data, allowing Auto Drive to retroactively apply background fixes smoothly and deterministically without derailing the primary goal trajectory.

## **Deterministic Completion Criteria and Operator Handoff**

A persistent challenge in autonomous systems is establishing precise, mathematical conditions for task completion, ensuring the agent hands control back to the operator appropriately rather than looping indefinitely or terminating prematurely1. Auto Drive resolves this by tying its completion criteria directly to the state of the FID backlog generated during the decomposition phase.  
The system relies on a Zero-Open-FID requirement. Auto Drive considers its primary macro-execution loop complete solely when a directory scan of dev/fids/ returns exactly zero files bearing the created, analyzed, fixed, verified, or converged statuses1. Every document initially generated by the Decomposition Engine must successfully navigate the entire Perfection Loop FSM, achieve a closed status with verifiable implementation evidence, and be physically moved by the Orchestrator to the dev/fids/archive/ directory2.  
Upon achieving a zero-queue state, Auto Drive initiates a final system certification process. The system engages the Scribe agent to parse the newly appended entries in the CHANGELOG.md file2, cross-referencing the aggregate completed work against the original one-sentence global\_goal provided by the operator. To guarantee final repository integrity, Auto Drive executes the /verify command, running all four supported core workspace typechecks to mathematically prove that no cascading breakages occurred during the autonomous run7.  
When certification passes, Auto Drive executes the operator handoff. The internal state machine transitions from active to complete, and the AgentActivity FSM sub-state indicator reverts to idle7. To provide the operator with a comprehensive, offline audit trail of the hours-long autonomous process, the system automatically executes the /export command, generating a fully self-contained, branded HTML session report that details every tool call, context compaction, and subagent invocation7. Finally, the system releases the terminal input lock, returning full interactive control to the human developer.

## **Failure Modes, Guardrails, and Risk Mitigation**

Deploying a fully autonomous agent within a production codebase introduces specific operational risks, notably infinite execution loops, unchecked scope creep, quality degradation over time, and rapid context exhaustion1. The Auto Drive architecture mitigates these risks by embedding Savant-Code's rigid governance directly into the lowest levels of the execution layer.  
Scope creep and the unauthorized deferral of complex tasks represent a primary failure mode; an autonomous agent may attempt to silently drop a difficult milestone to expedite completion1. Savant-Code fundamentally prohibits this behavior through an anti-deferral gate, rooted in ECHO Law 2 (Present Before Act)3. If the Thinker or Recorder agent attempts to modify a FID by marking a required module as "N/A" or deferring it to a future update, the EHEL framework detects the unauthorized scope reduction. Auto Drive immediately flags this violation, halts the FSM progression, transitions its macro-state to blocked, and surfaces a mandatory approval prompt to the operator via the OpenTUI interface. Auto Drive is physically incapable of bypassing the anti-deferral gate without a cryptographic receipt of operator consent1.  
A second critical vulnerability is the degradation of mechanical quality, specifically the hallucination of verification evidence. To expedite the AUDIT phase, an LLM might attempt to fabricate a passing test output2. Auto Drive neutralizes this risk by strictly enforcing the separation of duties. The Verifier agent possesses an empty tool schema (toolNames: \[\]) and is physically incapable of running tests3. Auto Drive relies entirely on the EHEL framework to securely execute the system commands and inject the raw stdout directly into the Verifier's prompt history2. If the EHEL injection fails or the test fails to compile, the Verifier is instructed to flag the issue as NEEDS-REVIEW8. Auto Drive interprets any NEEDS-REVIEW flag as a hard audit failure, immediately executing the SELF\_CORRECT fallback loop and ensuring that hallucinated success cannot bypass the FSM.  
Context exhaustion during the initial planning phase is prevented by applying strict blast-radius limits. If the operator provides an overly ambitious goal (e.g., "rewrite the entire frontend framework"), the Detective's initial query\_blast\_radius scan8 will return an excessive number of interconnected files. If the anticipated token payload of the resulting FIDs exceeds a predefined safety threshold, Auto Drive refuses to initiate the decomposition engine. It pauses execution, alerts the operator to the scale violation, and requires the human developer to divide the massive objective into smaller, sequentially manageable /goal requests, preserving the integrity of the underlying LLM processing window.

## **Phased Implementation Path**

The integration of the Auto Drive architecture into the existing Savant-Code monorepo must be executed progressively to avoid destabilizing the highly sensitive ECHO Harness Enforcement Layer and the 5,429+ passing tests1. The implementation is structured across a three-week rollout.

### **Week 1: State Management and The Continuation Driver (MVP)**

The first week focuses on establishing the core orchestration loop, transforming the manual Perfection Loop into a mechanically driven sequence.

* **Target Modalities:** cli/src/store/auto-drive-slice.ts (New), cli/src/commands/goal.ts, packages/agent-runtime/src/core/loop-driver.ts.  
* **Execution:** The development team will extend the existing Durable Goal Engine7, implementing an AutoDriveState slice within the Zustand store to manage the active | paused | blocked | complete tracking. A new ContinuationDriver class will be engineered to intercept the end\_turn signal. Instead of halting, the driver will programmatically invoke the transition\_phase tool, advancing the state from RED to GREEN to AUDIT based strictly on the metadata of the currently active FID.  
* **Deliverable:** A Minimum Viable Product (MVP) where a developer can manually generate a single FID, execute the /auto command, and observe the system autonomously drive the specific document through the execution phases without intermediate prompts.

### **Week 2: The Decomposition Engine and Autonomous Self-Healing**

The second week introduces the intelligence required to translate abstract goals and recover from inevitable failures.

* **Target Modalities:** agents/thinker/thinker.ts, packages/knowledge-graph/src/queries.ts, packages/agent-runtime/src/core/error-handler.ts.  
* **Execution:** The Thinker's sequentialthinking output schema2 will be hard-wired to output structured milestones, which are subsequently routed to the Recorder to systematically generate the dev/fids/ queue. Simultaneously, the FSM backward-transition logic will be implemented within error-handler.ts. This logic will capture specific EHEL rejections (e.g., failed builds, Law 1 read-before-write violations) and dynamically transition the loop back to the SELF\_CORRECT state, generating an error-correction prompt for the Forge agent.  
* **Deliverable:** The system will accept a one-sentence user goal, automatically decompose it into 3 to 5 highly structured FIDs, and systematically execute the queue, demonstrating autonomous recovery when the initial implementation fails compilation.

### **Week 3: Background Ghost-Commits and Bounded Memory Resilience**

The final week introduces the complex parallelization and long-session stability patterns pioneered by Every Code, ensuring the system can run for hours without degrading.

* **Target Modalities:** cli/src/workers/ghost-review.ts (New), protocol.config.yaml (Hooks section), packages/agent-runtime/src/memory/compaction.ts.  
* **Execution:** The parallel worktree architecture will be deployed. A Bun Worker thread will be bound to the PostToolUse lifecycle hook defined in protocol.config.yaml7. The system will duplicate the operational environment into .savant/worktrees/ghost-review/ and execute background verification passes. The resulting compliance\_warning receipts will be routed to the non-blocking update queue. Finally, the Immer destructive trims will be hardened across all TUI arrays to ensure memory footprint remains bounded.  
* **Deliverable:** A fully realized Auto Drive system. Code is systematically planned and implemented in the foreground, rigorously verified in the isolated background worktree, and seamlessly self-corrected, operating continuously until the dev/fids/ queue is exhausted and the final report is generated.

## **Synthesis**

The deployment of an Auto Drive system on top of Savant-Code represents a critical synthesis of unyielding governance and fluid operational autonomy. By architecting the system not as a separate, unrestrained agent, but as a mechanical continuation driver bound entirely by the ECHO Protocol v0.2.0, the framework retains its guarantees of mathematical correctness and strict separation of duties. The integration of Every Code's advanced paradigms—specifically decoupled background ghost-commits, rigid bounded state maps, and progressive auto-compaction—provides the necessary resilience for long-session, multi-hour execution. This blueprint ensures that when an operator defines a complex end goal, the resulting autonomous decomposition, planning, implementation, and verification phases are executed with absolute cryptographic provenance and mechanical rigor, culminating in a verified, shipped product without the necessity of human intervention.
