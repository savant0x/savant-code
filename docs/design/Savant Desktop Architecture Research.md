# **Savant-Code Desktop Architecture: Exhaustive Technical Report and Post-Perfection Loop Design**

The engineering mandate dictates the construction of a cross-platform native desktop application for Savant-Code, a terminal-native, multi-agent artificial intelligence coding assistant governed by the ECHO Protocol. Because the Savant-Code agent runtime is inextricably bound to the Bun runtime through native dependencies such as bun:sqlite, the architectural topography is strictly forced into a multi-process model. A Node.js or WebView-based user interface shell must execute a local bridge protocol to communicate with a deeply sandboxed Bun backend subprocess1.  
The following analysis exhaustively evaluates the technological stack required to deliver a secure, high-performance, and verifiable graphical wrapper. This wrapper must achieve a level of polish comparable to Hermes Desktop, while meticulously preserving the mechanical enforcement layer (EHEL) and Zero-Trust Agentic Provenance (ZTAP) inherent to the Savant-Code core framework1. The analysis synthesizes operating system constraints, cryptography requirements, local process bridge security paradigms, and generative user interface patterns to form a converged architectural blueprint.

## **Decision Questions and Architectural Verdicts**

### **Q1. UI Shell: Electron vs Tauri 2**

**Verdict:** Electron **Evidence:**  
\[cite: 3, 4, 5, 6\]  
**Confidence:** High  
The selection of the graphical user interface shell represents the most consequential infrastructure decision for a desktop application integrating complex terminal emulation and local sub-processes. While Tauri 2 offers significantly smaller packaged bundle sizes and reduced baseline memory footprints by leveraging OS-native webviews (WebView2 on Windows, WKWebView on macOS, WebKitGTK on Linux), this heterogeneity introduces unacceptable rendering risks for a highly complex coding assistant. The application relies heavily on xterm.js for terminal emulation, which utilizes a WebGL/Canvas renderer that requires absolute cross-platform consistency to avoid subtle text-rendering artifacts, latency spikes, and input-handling regressions3. The Chromium engine embedded within Electron guarantees a deterministic rendering pipeline across all operating systems, ensuring that hardware acceleration, font rendering, and DOM manipulation behave identically whether deployed on a Windows workstation or an Apple Silicon Mac.  
Furthermore, integrating node-pty to handle pseudo-terminal spawning natively requires consistent C++ bindings and predictable Node Application Binary Interface (ABI) compatibility. Electron natively provides this through its embedded Node.js environment, whereas Tauri would force the architecture into a convoluted Rust-to-Node.js interoperability layer just to manage the pseudo-terminal state4. Native modules in the Node ecosystem solve performance bottlenecks by writing C/C++ code that uses Node's N-API, compiling it to a .node file (a shared library). Because Electron uses a customized Node.js environment with a unique ABI, node-pty must be rebuilt specifically for the Electron version in use4. This recompilation pipeline is standardized and deeply integrated into the electron-builder and electron-rebuild toolchains.  
From an end-to-end testing perspective, Electron's maturity is unparalleled. Testing frameworks like Playwright offer native, first-class support for Electron applications, allowing automated suites to interact with the Chromium DevTools Protocol seamlessly. Tauri's WebDriver integrations, while improving, remain comparatively fragile for applications that require deep introspection of complex virtualized DOMs and WebGL canvas elements. Finally, Electron’s sophisticated auto-updating (electron-updater) and robust multi-process sandboxing (contextIsolation, sandbox) make it the most defensible choice for an application executing arbitrary local LLM-generated code. The memory overhead of bundling Chromium—typically ranging between 150MB to 300MB at idle—is a necessary and entirely acceptable trade-off for the deterministic execution of the React 19 UI, reliable WebGL terminal emulation, and seamless native module compilation.

### **Q2. Bundling Bun as a Platform Binary**

**Verdict:** Bundle the pinned Bun 1.3.14 executable via extraResources and recursively sign it using the mac.sign.binaries configuration matrix within electron-builder.**Evidence:**  
\[cite: 7, 8, 9\]  
**Confidence:** High  
Shipping a standalone Bun binary inside a desktop application is an established pattern, successfully utilized by prior art such as OpenHands (which bundles Python and Node.js distributions)1. However, the execution environment of a packaged Electron application introduces severe constraints regarding file access and cryptographic validation. Electron applications bundle their internal assets into an ASAR (Atom Shell Archive) format, which acts as a read-only, tar-like virtual filesystem7. Native binaries, including the Bun runtime executable, cannot be executed directly from within an ASAR archive because operating system loaders cannot map executable memory directly from an offset within a larger file. By configuring electron-builder to place the Bun binary in the extraResources directory, the executable remains unpacked and accessible via the process.resourcesPath API at runtime, allowing it to execute as a standard child process7.  
The critical complication arises from operating system security enforcement, specifically macOS Gatekeeper, Apple's Hardened Runtime, and Windows SmartScreen. To satisfy macOS Gatekeeper and notarization requirements, the bundled Bun binary must be explicitly code-signed. Apple’s Hardened Runtime strictly prevents the execution of unsigned third-party binaries embedded within an app bundle. Fortunately, electron-builder natively resolves this via the mac.sign.binaries configuration array, which instructs the osx-sign phase to individually sign the unpacked Bun executable before constructing the final DMG or PKG archive8. Without this recursive signing configuration, the build will either fail Apple’s automated notarization check or crash instantly upon user execution due to code signature validation failures.  
Furthermore, because the Bun runtime relies on the V8 JavaScript engine—which utilizes Just-In-Time (JIT) compilation to allocate executable memory dynamically—the macOS application must explicitly declare the com.apple.security.cs.allow-unsigned-executable-memory entitlement in its entitlements.mac.plist8. Failure to map this entitlement will cause the macOS kernel to terminate the Bun subprocess immediately upon boot due to memory protection violations. On the Windows side, placing the binary in extraResources ensures it is included in the Authenticode signing sweep, granting it the same SmartScreen reputation as the primary Electron executable.

### **Q3. Chat UI Stack for a Coding-Agent Transcript**

**Verdict:** @assistant-ui/react utilizing an ExternalStoreRuntime adapter.**Evidence:**  
\[cite: 10, 11, 12\]  
**Confidence:** Medium-High  
The visualization of a multi-agent coding transcript requires a rendering engine capable of handling extreme DOM pressure. The transcript must render streaming assistant text, structured tool-call interfaces (inputs, outputs, differential views), inline terminal emulation, and approval prompts, all while maintaining 60 frames-per-second scrolling performance across transcripts that may span tens of thousands of tokens. @assistant-ui/react provides the most mature, production-grade generative UI primitives available for the React 19 ecosystem, heavily outperforming custom Zustand implementations for features like auto-scrolling, virtualized thread lists, markdown rendering, and interactive tool-call approvals10. The Hermes Desktop reference architecture leverages this exact library to achieve its high level of polish1.  
While the Vercel AI SDK (ai \+ @ai-sdk/react) is excellent for server-to-client HTTP streaming and is already heavily utilized within the Savant-Code backend runtime, its frontend hooks are fundamentally coupled to HTTP endpoints and provider-specific data streams. Because Savant-Code operates a local Bun subprocess rather than a remote cloud endpoint, the UI must bridge a local protocol. The @assistant-ui/react ecosystem provides an ExternalStoreRuntime, a headless adapter designed specifically to map arbitrary external state—such as events streaming over a local process bridge—into the UI components without forcing HTTP transport or rigid server-sent events (SSE) parsing12.  
A critical risk factor associated with bleeding-edge React 19 libraries involves concurrent rendering anomalies. Recent analysis of the @assistant-ui/react repository reveals that under React 19 concurrent rendering, a bug within the underlying @assistant-ui/tap state management package caused frequent Version is less than committed version crashes during high-frequency agent streaming11. When a render lane was interrupted and React later replayed the reducer from an earlier base state (update rebasing), the local version counter fell behind the committed version, triggering an unconditional throw in the production build11. This bug was successfully patched in the @assistant-ui/react@0.15.1 and @assistant-ui/tap@0.3.31 releases by relaxing the guard to accept reducer replays. Recognizing and mitigating these React 19 specific concurrency issues is paramount for maintaining a crash-free chat transcript. The architectural decision remains firm on @assistant-ui/react, provided dependencies are strictly pinned above these patch versions.

### **Q4. Local Bridge Protocol Between the Bun Backend and the UI**

**Verdict:** JSON-RPC over stdio for standard process execution, evolving to Named Pipes / Unix Domain Sockets for detached daemon persistence.**Evidence:**  
\[cite: 6, 13\]  
**Confidence:** High  
Connecting the Electron main process (the Node.js environment governing the UI) to the sandboxed Bun backend subprocess requires a protocol that offers bidirectional streaming events, request/response command execution, backpressure management, and absolute, uncompromising security. The common paradigm of opening a local WebSocket or HTTP server on localhost (e.g., ws://localhost:8080) introduces critical, application-fatal security vulnerabilities. If the backend binds to a local network port, any malicious browser tab open on the host machine could execute Cross-Site WebSocket Hijacking (CSWSH) or DNS rebinding attacks to connect to the local agent backend. Given that the Savant-Code agent possesses filesystem write access and terminal execution capabilities, a hijacked local socket constitutes arbitrary Remote Code Execution (RCE) on the developer's machine.  
Communicating via standard input/output (stdio) perfectly mitigates this threat vector. By utilizing stdio, the Electron parent process and the Bun child process establish a secure, anonymous pipe directly orchestrated by the operating system kernel. This communication channel is entirely invisible to the host network stack, eliminating the possibility of port-scanning or unauthorized cross-origin access. JSON-RPC serves as the ideal payload formatting standard over this pipe, allowing for multiplexed streams representing assistant text, tool calls, phase transitions, and diffs.  
If the application design eventually requires the agent to continue executing autonomous, long-running tasks (such as the Savant-Code /auto-drive budgeted goal mode) even when the Electron UI window is closed, the architecture must evolve into a detached daemon model. In this scenario, stdio is insufficient because the child process is traditionally bound to the parent's lifecycle. To achieve a persistent daemon that survives UI restarts—a pattern utilized successfully by integrated terminal systems like Superset—the backend must bind to an OS-level socket: Unix Domain Sockets (.sock files) on macOS/Linux and Named Pipes on Windows6. These mechanisms retain stringent filesystem-level access control permissions (preventing unauthorized processes from connecting) while allowing the Electron UI to detach and reattach seamlessly to a persistent background agent loop6.

### **Q5. Exposing an ACP (Agent Client Protocol) Server**

**Verdict:** Expose ACP via stdio as a secondary backend interface, but prioritize the proprietary ECHO-specific JSON-RPC bridge for the v1 release.**Evidence:**  
\[cite: 13, 14, 15, 16\]  
**Confidence:** Medium  
The Agent Client Protocol (ACP) is rapidly crystallizing as the standard communication interface between code editors and generative AI agents, effectively positioning itself as the "Language Server Protocol (LSP) for AI agents"15. Driven by organizations like Zed Industries, ACP standardizes communication for common agentic tasks, utilizing JSON-RPC over stdio for local agents and providing a robust capability negotiation phase where clients and agents agree upon supported features (e.g., file reading, image content support, session persistence)13.  
If Savant-Code were to expose an ACP-compliant server, it would immediately unlock interoperability with external IDEs like Zed, Neovim (via CodeCompanion), or standard Emacs shells15. However, ACP is fundamentally designed as a bidirectional interface where the *agent* requests file operations from the *client* (the editor), allowing the agent to read the editor's active state and modify files within the IDE's virtual buffers16.  
Savant-Code operates under a highly opinionated, heavily governed runtime defined by the ECHO Protocol. It possesses its own internal tool registry, mechanical enforcement layers (EHEL), and the Zero-Trust Agentic Provenance (ZTAP) framework, which demands hash-only, per-role Ed25519-signed write receipts at the native filesystem boundary1. Mapping the ECHO Protocol's 15 laws, its strict 10-agent separation of duties (Detective, Forge, Verifier, Adversary), and its Perfection Loop state machine onto the generic ACP schema introduces significant abstraction overhead for the primary desktop client.  
Therefore, for the v1 Electron application, constructing a bespoke JSON-RPC bridge tailored explicitly to the ECHO Protocol’s exact state transitions and ZTAP signature validations provides tighter integration and superior security guarantees. ACP compatibility must be slated as an immediate v1.1 fast-follow. Exposing a secondary ACP server endpoint will allow Savant-Code to function as a backend brain for other editors, multiplying its market reach without compromising the specialized governance of its primary desktop interface.

### **Q6. Distribution, Auto-Update, and Signing Pipeline**

**Verdict:** electron-builder coupled with electron-updater, utilizing GitHub Releases as the update feed, secured by Azure Trusted Signing for Windows and standard Apple Developer ID notarization for macOS.**Evidence:**  
\[cite: 8, 9, 18, 19, 20, 21\]  
**Confidence:** High  
The distribution and auto-update mechanics of a desktop application determine its long-term viability and security posture. electron-builder remains the undisputed industry standard for packaging multi-target desktop applications, natively integrating with electron-updater to pull delta updates from generic cloud storage or GitHub Releases9. The primary challenge in desktop distribution is navigating the labyrinthine requirements of OS-level cryptographic code signing.  
For macOS, distributing applications outside the Mac App Store requires an Apple Developer ID Application certificate. The application must be code-signed and subsequently uploaded to Apple's notary service to receive a notarization ticket. If an application is not notarized, macOS Gatekeeper will explicitly block its execution on macOS 10.15 and later. electron-builder handles this notarization pipeline automatically, requiring only the injection of the APPLE\_ID, APPLE\_APP\_SPECIFIC\_PASSWORD, and APPLE\_TEAM\_ID (or equivalent API keys) into the CI environment8.  
The Windows signing ecosystem has historically been highly problematic for open-source and automated CI/CD pipelines. Standard Organization Validation (OV) certificates subject new applications to severe Windows SmartScreen "Unknown Publisher" warnings until a sufficient, opaque volume of downloads establishes reputation. Extended Validation (EV) certificates bypass SmartScreen immediately but mandate that the private cryptographic key resides on a physical hardware token (HSM) or a strict cloud HSM, effectively breaking standard GitHub Actions pipelines18.  
Microsoft recently disrupted this paradigm with the release of Azure Trusted Signing (formerly Azure Artifact Signing). This service acts as a modern, cloud-based signing backend that completely eliminates the need for physical HSM tokens or local .pfx files while instantly granting SmartScreen reputation18. electron-builder (v25+) offers native integration with this service via the win.sign.type: "azure" configuration. By configuring the Azure Tenant ID, Client ID, and Client Secret in the CI environment, the GitHub Action can authenticate with Microsoft Entra ID and cryptographically sign the .exe and NSIS installers dynamically21. This represents a monumental shift for Windows distribution, reducing costs and entirely removing the friction of hardware tokens.

## **Final Recommended Stack**

The definitive architectural stack for the Savant-Code desktop application is composed of the following orchestrated technologies:

* **Shell Context:** Electron (v31+), providing absolute WebGL determinism and robust multi-process sandboxing.  
* **Build Pipeline:** Vite via electron-vite, ensuring rapid hot-module replacement and optimized asset bundling.  
* **User Interface:** React 19 driven by @assistant-ui/react and styled via Tailwind CSS v4, yielding a highly performant generative UI capable of handling streaming tool-calls.  
* **Bridge Protocol:** JSON-RPC multiplexed over local stdio, mapped into the UI via ExternalStoreRuntime, guaranteeing total network isolation.  
* **Terminal Emulation:** xterm.js paired with node-pty, spawned securely within the sandboxed Bun subprocess and bridged via RPC to the UI.  
* **Distribution Packaging:** electron-builder generating macOS universal binaries (DMG), Windows NSIS installers, and Linux AppImage/deb/rpm packages.  
* **Update Mechanics:** electron-updater executing seamless delta updates sourced from GitHub Releases.  
* **Cryptographic Pipeline:** Apple Developer ID with automated notarization for macOS, and Azure Trusted Signing executing cloud-based SmartScreen-compliant signatures for Windows.

This stack maximizes the reuse of Savant-Code's existing React 19 UI assets while providing the most stable, battle-tested multi-process shell available. Electron ensures absolute consistency for WebGL-based terminal rendering, while electron-builder seamlessly resolves the complex cryptographic signing requirements across modern operating systems. Utilizing JSON-RPC over stdio strictly isolates the execution environment, neutralizing severe network-based attack vectors.

## **Six-Month Horizon Note**

The selected technology stack is strategically positioned to support immediate product launch requirements, but specific components require rigorous monitoring as the ecosystem shifts over the next six to twelve months.  
The adoption of Azure Trusted Signing fundamentally future-proofs Windows distribution, bypassing the draconian hardware token requirements historically mandated by the CA/Browser Forum and streamlining CI/CD automation18. The use of JSON-RPC over stdio provides an inherently secure IPC model that aligns with enterprise-grade deployment standards.  
However, the Agent Client Protocol (ACP) is maturing aggressively and establishing significant market penetration13. While a bespoke JSON-RPC bridge is strictly recommended for v1 to ensure adherence to the nuanced ECHO Protocol laws and ZTAP verification, adopting ACP natively within six months will be necessary to allow cross-pollination with other integrated development environments in the ecosystem. Furthermore, while Electron is the safest choice today due to unparalleled WebGL stability for xterm.js, Tauri 2.0 is stabilizing rapidly. If the underlying OS-native webviews (specifically Windows WebView2) achieve strict parity in HTML5 Canvas rendering performance, migrating the UI shell to Tauri in late 2026 or 2027 could reduce the baseline memory overhead and application footprint by over 100MB, presenting a highly attractive optimization vector.

## **Open Questions**

Before initiating the active build phase, the engineering leadership must resolve the following architectural ambiguities to ensure alignment with product requirements:

> 1. **Daemonization Persistence:** If the user actively closes the main Electron window during a heavily budgeted, long-running /auto-drive operation, should the Bun subprocess terminate immediately (standard child process behavior), or should it run as a detached daemon allowing the UI to re-attach upon subsequent relaunch6?  
> 2. **Secret Management Integration:** The existing Savant-Code CLI stores provider keys in a local credentials.json plaintext file1. Will the desktop application continue to read from this file for parity, or should the architecture migrate credential storage into the native OS cryptographic keychains (macOS Keychain, Windows Credential Manager) via keytar or similar native modules for enhanced security?  
> 3. **Terminal Bifurcation:** Should the embedded terminal utilize node-pty instances spawned directly by the Electron main process for lower latency, or should all terminal execution be routed entirely through the sandboxed Bun backend via the native bash tools defined in the ECHO protocol? Routing through Bun centralizes the ZTAP cryptographic receipts but introduces IPC latency overhead for interactive TTY applications like vim or htop.

## **Post-Perfection Loop Converged Plan**

To finalize the architectural blueprint, the system design must be re-evaluated through the lens of the ECHO Protocol. The desktop application must synthesize the technological stack into the stringent, non-negotiable governance models of the 15 Laws, the mechanical enforcement layer (EHEL), the Zero-Trust Agentic Provenance (ZTAP) framework, and the state transitions of the Perfection Loop1. Furthermore, specific considerations must account for development operations based within the United States.

### **Mechanical Integration of the ECHO Protocol (EHEL)**

The desktop application shell must act as a strict visualizer and facilitator of the ECHO protocol; it must never attempt to replicate or enforce the protocol logic client-side. The Bun backend maintains absolute, cryptographic authority over the Finite State Machine (FSM). The JSON-RPC stdio bridge will emit typed state transitions reflecting the exact phase of the Perfection Loop (idle, red, green, audit, adversarial, self\_correct, complete)17.  
The @assistant-ui/react front-end, augmented by the ExternalStoreRuntime, must map these distinct states directly into contextual user interface alterations:

* **RED Phase (Detective):** When the backend transitions to red, the UI must visually lock standard chat inputs to signify autonomous analysis. It will display a dedicated "Codebase Analysis" panel, rendering the specific file:line grep outputs and call-graph blast radii dynamically queried by the Detective agent, providing visual proof of Law 1 (Read 0-EOF) compliance1.  
* **GREEN Phase (Forge):** During the green implementation phase, the UI will capture the write\_file and apply\_patch tool calls. Instead of simple text blocks, these payloads must route into a Monaco Editor-backed differential viewer, rendering the 50% neon green and red overlays mandated by the Savant-Code design system2.  
* **AUDIT / ADVERSARIAL Phase Hard Stops:** When the Verifier agent executes its double-audit, the Electron shell will pipe the raw test and lint terminal outputs (via the backend node-pty instance) directly into the chat transcript. To satisfy Law 2 (Present Before Act) and the explicit approval mechanics of STRICT mode, the UI must expose a cryptographic "Approve & Apply" button, forcing the human operator to manually unblock the loop1.

### **Zero-Trust Agentic Provenance (ZTAP) Verification Boundary**

The ZTAP framework mandates that every agent action—especially filesystem modifications—generates a hash-only, per-role Ed25519-signed write receipt appended to an immutable session ledger2. Because the Electron UI operates as a separate operating system process, it must be treated as an untrusted client rendering a trusted state.

* The isolated Bun subprocess utilizes its embedded cryptographic libraries to generate the Ed25519 signatures for every state change or filesystem write.  
* The JSON-RPC bridge transmits the raw payload alongside its corresponding cryptographic signature.  
* The Electron preload.js script (running with Node integration enabled, but strictly separated from the renderer via contextIsolation) intercepts this payload. It mathematically verifies the signature against the public key of the active session before injecting the data into the DOM. This architecture guarantees that even if the inter-process communication pipe is theoretically intercepted or spoofed, the UI will reject the rendering of any operation that lacks a valid signature sanctioned by the mechanical EHEL gate.

### **Separation of Duties in Terminal Emulation**

The ECHO protocol explicitly demands the separation of duties: the Forge agent that writes the code cannot be the agent that verifies it1. To accurately support this strict separation in the desktop client, the terminal architecture must be bifurcated into two distinct streams:

> 1. **User-Facing Interactive Terminal:** A standalone xterm.js instance, backed by a dedicated node-pty process, allowing the human operator to run manual, unlogged system commands freely.  
> 2. **Agent-Facing Immutable Terminal:** A completely headless node-pty instance managed exclusively by the Bun subprocess. When the Verifier or basher agent executes run\_readonly\_command or validation commands (commands.test) from the protocol.config.yaml, the standard output and error streams are intercepted by Bun, parsed for the Feature Implementation Document (FID), and simultaneously multicast over the JSON-RPC bridge. The UI renders this specific stream in a read-only, locked xterm.js block embedded directly within the React 19 chat transcript. This guarantees that audit evidence is immutable and easily traceable by the human operator.

### **Convergence on United States Export and Corporate Verification Constraints**

Because the core development and initial distribution of this software originate within the United States, strict compliance with corporate identity verification and cryptographic export regulations must be heavily integrated into the automated CI/CD release pipeline.  
The implementation of Azure Trusted Signing requires the owning U.S. corporate entity to undergo rigorous, standard identity verification via Microsoft Entra ID21. Similarly, Apple Developer Program enrollment mandates a valid U.S. DUNS number and corporate verification for the generation of Developer ID certificates required for macOS DMG notarization8.  
To ensure the security of the release process, the Electron afterPack lifecycle hooks must be strictly configured to execute the codesign and Azure signtool processes exclusively within secured, ephemeral GitHub Actions runners. This guarantees that the private Azure App Registration secrets, Microsoft Entra ID tokens, and Apple App-Specific Passwords never reside on local developer workstations, preventing the accidental leakage of highly sensitive U.S. corporate cryptographic signing authority22. This zero-trust approach to the build pipeline mirrors the ZTAP philosophy of the application itself, ensuring a cryptographically sound, fully verifiable software supply chain.
