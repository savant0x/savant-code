# **SkillOpt Integration into Savant-Code's Self-Improving Harness: An Architectural Blueprint**

The convergence of Microsoft’s SkillOpt text-space optimization paradigm with the Savant-Code multi-agent framework represents a profound inflection point in autonomous capability evolution. SkillOpt introduces a rigorous, neural-network-inspired approach to prompt and skill optimization, treating natural language markdown documents as the trainable state of a frozen agent1. By utilizing iterative rollouts, reflective analysis, bounded text edits, and held-out validation gates, SkillOpt successfully mimics gradient descent in the semantic space without touching underlying model weights4. The recent introduction of the SkillOpt-Sleep deployment companion extends this from benchmark environments to real-world, nightly session harvesting, providing a direct conceptual parallel to Savant-Code’s existing self-improving harness7.  
However, the architectural integration of these two systems cannot be a mere mechanical port. Savant-Code operates within a highly constrained, deterministic TypeScript/Bun environment governed by the ECHO Protocol (v0.2.0)9. It strictly enforces a single-model project-wide constraint, mandates operator-only trust boundaries via Zero-Trust Agentic Provenance (ZTAP), and actively suppresses the silent mutations that are often acceptable in research-grade Python frameworks11. Furthermore, a comprehensive audit of the Savant-Code origin repository (verified 2026-09-09) reveals that while the foundational stage wiring for self-improvement exists, critical degradation has rendered the loop largely inert11. Quarantined drafts sit unseen, the recurrence deduplication key is critically flawed in both directions, and a destructive thirty-day purge default threatens to silently destroy operator-directed edits11.  
This research report delivers an exhaustive, expert-level integration blueprint designed to transplant the mathematically rigorous concepts of SkillOpt—specifically its validation gating, edit bounding, and context isolation mechanisms—into the robust, operator-governed shell of Savant-Code. The analysis provides deep architectural resolutions to the identified failures, rejecting incompatible SkillOpt paradigms while adapting its highest-leverage workflows into an ordered sequence of Feature Implementation Documents (FIDs) sized explicitly for the ECHO Perfection Loop.

The intersection of SkillOpt’s stochastic evolution and Savant-Code’s deterministic governance requires precise boundary mapping. The following matrix delineates the core mechanisms of SkillOpt, identifies their corresponding execution seams within Savant-Code, and delivers an authoritative verdict on their integration viability based on the hard constraints of the ECHO Protocol.

| :---- | :---- | :---- | :---- |

However, Savant must adapt SkillOpt's semantic task grouping (skill\_hint) to resolve its current over-fragmentation bug11. |

## **Architectural Decision Records: Resolving the Integration Seams**

The subsequent sections explore the eight core research questions, analyzing the theoretical underpinnings of both systems and establishing a definitive architectural blueprint for each integration seam.

### **1\. Staging and Adoption User Experience**

The operational visibility of proposed skill updates fundamentally dictates the efficacy of any self-improving system. In SkillOpt-Sleep, the skillopt-sleep status command defaults to surfacing the latest staged proposal, placing the onus of review directly in the operator's path7. The system is designed around the "review, then adopt or discard" contract, explicitly expecting the human to interact with the staging boundary17.  
Conversely, the 2026-09-09 audit of Savant-Code reveals a critical failure in operational visibility. Three quarantined drafts currently sit unseen in the repository, committed incidentally by tree-drain actions rather than conscious operator trust11. The session-end-review.ts script lacks notification mechanisms, and the /skills command defaults to the trusted view, requiring the operator to proactively supply the \--quarantined flag to discover pending work11. This design creates an epistemic void where the agent generates improvements that die in obscurity.  
**Verdict:** Savant-Code must invert its default disclosure heuristics across all administrative surfaces. The /skills command must display the quarantine by default when drafts are present, and the mechanical harness must emit deterministic, high-visibility notifications via the SessionEnd hook and the OpenTUI boot sequence.  
**Integration Blueprint:** The integration touches three distinct architectural surfaces to map SkillOpt's visibility onto Savant's constraints. First, the mechanical scripts/session-end-review.ts script—which executes deterministically via the SessionEnd hook without LLM intervention—must be expanded11. After refreshing the dev/agenda.md file, the script must parse .agents/skills/.quarantine/VERSIONS.jsonl. If unreviewed drafts exist, it must write a highly visible block to standard output: \[\!\] System Alert: {N} mechanically drafted skills are pending operator review. Execute /skills to inspect.  
Second, the OpenTUI React CLI (cli/src/components/) requires a deterministic startup check. A persistent sidebar badge, labeled Skills \[{N}\], must render in the primary navigation column when the local .quarantine directory contains active entries. This provides continuous, non-intrusive awareness of the queue depth.  
Finally, the cli/src/commands/skills.ts module must have its default argument inverted. When the operator executes /skills without arguments, the routing logic must check the quarantine ledger. If pending drafts exist, the command must automatically route to the \--quarantined view, displaying the pending proposals. The live, trusted skills would subsequently be accessible via an explicit /skills list \--trusted command. This inversion forces the operator to confront the agent's proposed evolution, fulfilling the ECHO Protocol's "Present Before Act" mandate9.

### **2\. Gate-Before-Present Machinery**

The integrity of a self-evolving system relies entirely on its validation gating. SkillOpt's architecture dictates that a candidate edit is accepted only when it strictly improves a held-out validation score2. This verifier-discipline prevents the accumulation of reward-hacking artifacts—rules that improve surface-form compliance but degrade grounded task success15. In Savant-Code, the proof machinery (skills prove) exists, featuring paired baseline/skill-active trials and erosion gating, but it operates in a strictly advisory capacity at trust time and is completely unwired from the initial presentation to the operator11.  
Savant cannot run isolated target-model verification during the Scribe's drafting phase. Doing so would violate the single-model constraint by monopolizing the operator's primary inference stream, effectively freezing the interactive session11. The architecture requires bifurcating the gate into a synchronous mechanical phase and an asynchronous evaluation phase.  
**Verdict:** Implement a two-stage gating architecture. A deterministic syntax, schema, and Levenshtein gate runs immediately upon draft generation. Subsequently, the skills prove machinery runs asynchronously as a background process. Drafts presented to the operator before proof completion, or those that fail the proof, must be aggressively labeled as \[⚠ UNPROVEN — TRUSTING BLIND\].  
**Integration Blueprint:** When the Scribe generates a .quarantine draft via lessons:to-skills, the ECHO Harness Enforcement Layer (EHEL) must instantly execute a deterministic parser10. This phase requires zero model calls. It verifies that the markdown is structurally well-formed, checks for illicit payload secrets, and calculates the exact Levenshtein character change ratio against the baseline, ensuring it remains beneath the 10% maximum oscillation threshold9.  
The second phase hooks into the SessionEnd lifecycle event20. The skills prove capability is executed as a background subprocess, utilizing the operator's single model. It orchestrates a paired-lift trial, running the exact failure trace that triggered the draft against both the baseline skill configuration and the newly proposed configuration. It calculates the pass@k capability and pass^k reliability.  
When the operator opens the /skills view, the UI renderer inspects the draft's metadata. If the asynchronous proof has not completed, or if the erosion gate detected a performance regression, the draft title must be rendered in high-contrast red with the prefix \[⚠ UNPROVEN — TRUSTING BLIND\]. If the proof succeeds, demonstrating verifiable lift, the subsystem appends a signed Zero-Trust Agentic Provenance (ZTAP) receipt to the ledger (provenanceRef: proof:\<sha\>) and renders the draft with a \[✓ PROVEN\] badge10. This maintains the operator-only trust boundary while providing the rigorous empirical data demanded by the SkillOpt philosophy.

### **3\. Purge Semantics and Backup Contracts**

The handling of rejected or stale skill drafts determines the long-term safety of the evolution loop. In SkillOpt, the adopt() function carefully backs up every live file before overwriting it16. However, this implementation possesses a fatal flaw (Issue \#247): the backup unconditionally overwrites the backup/ directory. If an operator accidentally adopts the same staging directory twice, the original backup is permanently overwritten by the regressed proposal, completely destroying the rollback path16.  
Savant-Code currently suffers from a different, yet equally severe, degradation: the purgeRejectedDrafts utility implements a destructive 30-day deletion of any never-trusted draft11. This design silently destroys pending operator-directed edits if they sit unreviewed, violating the core invariant that the harness cannot forget and must not silently mutate the workspace.  
**Verdict:** The destructive purgeRejectedDrafts utility must be deprecated entirely. It is to be replaced with a monotonic, move-only expiration contract that archives drafts. Furthermore, Savant must rely on its existing cryptographic prevSha ledger for rollbacks, explicitly rejecting SkillOpt's fragile filesystem backup approach.  
**Integration Blueprint:** The scripts/lessons-to-skills.ts pipeline must be rewritten. Instead of executing an rm operation after 30 days, the script will invoke a standard fs.rename, moving the unreviewed draft from .agents/skills/.quarantine/ to an append-only archive directory at .agents/skills/.quarantine/.archive/YYYY-MM/. Simultaneously, the VERSIONS.jsonl ledger must record a state transition to {"action": "archived"}. This preserves the historical record of the LLM's reasoning without bloating the active quarantine loader's context window.  
For the adoption and rollback contract, Savant must explicitly ignore SkillOpt's \_backup method. When an operator runs /skills trust \<name\>, the EHEL mechanism will take the current live SKILL.md and snapshot it into .agents/skills/\<name\>/versions/v\<N\>/SKILL.md13. The newly trusted draft is then moved into the live position. The ledger records {seq, action: "trust", prevSha, nextSha, provenanceRef}13.  
By utilizing an append-only versions/v\<N\> directory structure and a cryptographic ledger, Savant entirely neutralizes the failure mode of SkillOpt's design. At 1000 drafts, an archive directory incurs negligible inode overhead and zero context cost, while the monotonic ledger guarantees that a rollback command can endlessly traverse the history without ever clobbering a previous state.

### **4\. Skill-Edit Proposals and Content Drift**

Effective review of proposed skill modifications requires high-fidelity differentiation between the baseline and the candidate. SkillOpt stages per-skill proposals pinned to live baselines, calculating a sha256 hash of the live bytes at consolidation time, and strictly refuses publication if the live file has drifted prior to adoption11. In the current Savant-Code deployment, pending edits (such as the release-workflow update from 2026-09-08) remain entirely invisible to the operator, leading to active content drift where the live skill ships superseded information while the unreviewed draft decays in quarantine11.  
**Verdict:** Savant-Code must surface pending edits as reviewable unified diffs within the TUI. A strict baselineSha drift-detection mechanism must be implemented at the trust boundary to definitively refuse operator adoption if the live skill has been modified since the draft's creation.  
**Integration Blueprint:** The raw material for diff generation already exists within the patch action data and the VERSIONS.jsonl ledger11. The cli/src/commands/skills.ts module must be updated to intercept the /skills show \<name\> \--quarantined command. Instead of rendering the raw markdown blob, the CLI must perform a dynamic comparison between the quarantine draft and the live .agents/skills/\<name\>/SKILL.md. The output must be a standard unified diff, utilizing the established OpenTUI formatting: tinting added lines 50% neon green and removed lines 50% neon red, accompanied by an \[-N/+M\] add/remove counter10.  
To address content drift, the skill\_manage tool handler must inject a baselineSha parameter into the draft's metadata at the moment of creation. This hash represents the exact byte state of the live skill when the Scribe authored the patch. When the operator executes /skills trust \<name\>, the EHEL gate must recalculate the SHA of the live skill.  
If currentLiveSha \!== draft.baselineSha, the operation must immediately halt, throwing a fatal terminal error: Drift detected: The live skill has been modified since this draft was authored. Trust refused. Execute /skills rebase \<name\> to regenerate the draft against the current baseline. This deterministic block ensures that manual operator edits are never silently clobbered by stale, asynchronous harness drafts.

### **5\. Recurrence and Skill Identity Mapping**

The transition from a raw failure trace to a stabilized skill identity dictates the noise-to-signal ratio of the self-improving harness. The 2026-09-09 audit reveals that Savant's recurrence deduplication key is catastrophically broken in both directions. Originally, over-merging collapsed disparate failures into a generic "tool result contains an error" string11. Post-fix, the inclusion of payload-embedded error lines (e.g., timestamps, specific file paths) assigns every distinct failure a mathematically unique key, resulting in massive over-fragmentation where the recurrence \>= 3 threshold is never achieved11.  
Conversely, SkillOpt utilizes a more nuanced grouping strategy. Task miners extract a skill\_hint from the trace, grouping tasks by these hints so that edits are routed to specific, relevant skills rather than a monolithic catch-all file (Issue \#120)14.  
**Verdict:** The deduplication key must transition from a raw payload string to an aggressively stripped topological hash. Furthermore, the Scribe must adopt SkillOpt's skill\_hint clustering to map recurrences to distinct existing skills.  
**Integration Blueprint:** The common/src/util/experiences.ts normalization function requires an immediate rewrite. Before computing the SHA256 hash, the errorFirstLine must pass through a strict regex sanitization pipeline. This pipeline must forcefully strip absolute and relative file paths, hex memory addresses, UUIDs, and quoted string literals. For example, an error reading tsc: error TS2322: Type 'string' is not assignable to type 'number' at src/components/ui.tsx:42 must be reduced to its topological skeleton: tsc: error TS2322: Type is not assignable to type.  
The deduplication key becomes sha256(toolName \+ strippedError). This guarantees that identical structural failures trigger the recurrence threshold regardless of the specific file or variable involved. However, the dev/agenda.md presentation must retain the original, unstripped payload sample to provide the operator and the Scribe with the necessary context for drafting the rule.  
Once the threshold is met, the Scribe session-end review must be prompted to extract a skill\_hint from the clustered errors. By analyzing the tool name (e.g., run\_terminal\_command with tsc) and the error domain, the Scribe will map the recurrence to an existing .agents/skills/ file (e.g., typescript-strict.md). If a mapping exists, it drafts a patch proposal for that specific skill. If the structural failure is novel, it generates a create proposal. This fan-out ensures the agent's specific competencies evolve independently.

### **6\. Handoff Mode and Context Contamination**

When an LLM reflects on its own failure traces, it is highly susceptible to context contamination—over-indexing on the specific phrasing or conversational traps of the prior session, leading to shallow, reward-hacking rules (Goodhart's Law)15. SkillOpt mitigates this via the handoff backend. This mode runs the cycle without any model subprocess, writing pending model calls to pending.json and PROMPTS.md (exit code 3). This forces the human or a completely fresh-context agent to answer the prompt, guaranteeing isolation17.  
Savant's Scribe currently drafts skills with full message history, exposing it to the exact contamination class SkillOpt explicitly engineered away11.  
**Verdict:** Savant must adopt a native equivalent to SkillOpt's handoff isolation. The Scribe must be cold-spawned with includeMessageHistory: false, receiving only structured, deduplicated input to force generalized root-cause analysis.  
**Integration Blueprint:** The integration occurs at the Orchestrator's end-of-turn directive that initiates the Scribe session-end review13. The spawn parameters must be explicitly modified to include the SDK flag includeMessageHistory: false9. This severs the Scribe's access to the conversational back-and-forth that preceded the failure.  
The Scribe's system prompt must then be dynamically constructed using strictly isolated inputs. The engine will inject the output of the mechanical session-end-review.ts script (the ≤50 line dev/agenda.md) and the specific, filtered array of raw-traces.jsonl entries that crossed the deduplication threshold11.  
By depriving the Scribe of the parent agent's frustrated attempts and reasoning loops, the system enforces epistemic hygiene. The model is forced to evaluate the bare mechanics of the failure and draft a rule that addresses the structural deficit, directly mirroring the mathematical isolation achieved by SkillOpt’s HandoffBackend without requiring complex file-based exit-code loops.

### **7\. Explicit Rejections: What Savant Must Not Adopt**

To maintain the architectural integrity of the ECHO Protocol, several core SkillOpt mechanisms must be explicitly rejected. The integration must not compromise Savant's constraints in pursuit of optimization parity.

| SkillOpt Mechanism | Rationale for Rejection | Systemic Implication |
| :---- | :---- | :---- |
| **Separate Optimizer Model** | SkillOpt relies on a heavy frontier model (e.g., GPT-4) to optimize skills for a smaller target model (e.g., Qwen)1. This violently violates Savant's "Single model project-wide" constraint11. | Savant users often operate in local-first, air-gapped environments via Ollama10. Mandating a second, heavier model for the optimization loop breaks the core product promise and introduces unacceptable API cost multipliers. Reflection must occur via the user's selected model. |
| **Benchmark Replay / Contrastive Reflection** | SkillOpt replays tasks multiple times offline to generate contrastive mini-batches of successes and failures5. | In a deployment companion running on a user's workstation, silently spinning up massive background rollouts consumes unacceptable compute and token budgets. Savant must rely strictly on organic *usage evidence* captured during actual human-directed sessions13. |
| **Dream Rollouts (Synthetic Tasks)** | SkillOpt-Sleep allows "dream rollouts" where the agent hallucinates synthetic tasks to practice on7. | This introduces massive hallucination risk into the ZTAP governance model. Rules derived from synthetic tasks optimize for imaginary environments. Savant must only optimize against ground-truth failures that actually blocked real user intent. |
| **Python Runtime Architecture** | SkillOpt is a Python ≥3.10 package (skillopt-sleep)7. | Savant is a rigidly pinned Bun 1.3.14 TypeScript strict monorepo10. Engine code translation is rejected; only the theoretical contracts (validation gates, textual learning rates, handoff isolation) are ported to TypeScript abstractions. |
| **Unattended Auto-Adoption** | SkillOpt permits \--auto-adopt configurations that rewrite live skills unattended (e.g., via cron)16. | This violates the absolute "Operator-only trust" invariant11. Nothing in Savant auto-promotes. The operator must remain the final arbiter of system capability. |

## **Risk Register and Honest Boundaries**

Integrating an automated, self-evolving engine into a deterministic, ZTAP-governed framework introduces systemic risks that must be continuously managed.  
The primary risk is **Operator Alert Fatigue**. If the recurrence threshold is calibrated too aggressively, the Scribe will flood the quarantine with hyper-specific, low-leverage drafts. While the default-inversion of the /skills command mitigates invisibility, an overwhelming volume of drafts will condition the operator to ignore the interface entirely, effectively neutralizing the human-in-the-loop safeguard. This risk is actively managed by the hard 50-line cap on dev/agenda.md, which physically constrains the Scribe to authoring only 1-3 high-leverage drafts per session11.  
A secondary risk involves **False-Positive Deterministic Gates**. A syntax and schema gate may successfully pass a skill edit that is structurally flawless but semantically destructive (e.g., a properly formatted markdown rule that instructs the agent to "always bypass test failures"). The deterministic gate proves that the skill does not break the harness infrastructure; it cannot prove that the skill's logic is benign.  
This necessitates the enforcement of absolute **Honest Boundaries**. It must be explicitly communicated to the operator that Zero-Trust Agentic Provenance (ZTAP) proves the *mechanical process* of the draft's creation, not the *epistemic quality* of the LLM's reasoning10. A ZTAP receipt on a quarantined skill guarantees it was authored by the Scribe in response to a mechanically tracked failure trace; it provides zero mathematical guarantee that the resulting rule is correct or safe. The operator's manual verification via /skills show \<name\> \--quarantined remains the irreducible, final boundary for system integrity. The harness proposes; the human disposes.
