# **Savant-Code Evaluation System Architecture: Harness Testing and Grading Landscape Blueprint**

## **Executive Summary**

The rapid maturation of the Savant-Code ecosystem—marked by the introduction of agent-created skills, holographic command deck interfaces, and rigid adherence to the ECHO Protocol v0.2.0—demands a fundamental restructuring of its evaluation infrastructure1. The existing @savant-code/evals (benchmark v2) framework operates effectively as a deterministic task runner, utilizing curated YAML files to feed tasks into an isolated sandbox environment and validating check commands1. However, the v2 architecture predates the dynamic generation of SKILL.md artifacts authored by the agents themselves1. Consequently, it lacks the mathematical primitives required to validate the statistical efficacy of these dynamic skills, the analytical depth to prevent architectural erosion during long-horizon self-improvement loops, and the architectural agility to operate seamlessly in a Windows-first, Docker-less environment.  
This comprehensive report provides an exhaustive architectural blueprint for rebuilding the Savant-Code evaluation system. Through a meticulous analysis of fourteen prevailing open-source evaluation frameworks operating in the 2025–2026 landscape, the analysis distills critical methodologies into actionable Architectural Decision Records (ADRs). The subsequent blueprint establishes a transition to a Bun-native, temporary-directory sandboxing model that bypasses Docker overhead on Windows systems. It introduces a stratified testing philosophy that strictly separates capability discovery from regression guarding. Furthermore, it mandates the integration of a mathematically rigorous skill-efficacy grading engine based on probabilistic pass rates, ensuring that the self-improving harness generates empirically validated code without sacrificing the stringent governance structures mandated by the ECHO Protocol.

## **The Evaluation Landscape Analysis**

The contemporary landscape of open-source artificial intelligence evaluation frameworks is highly fragmented, with distinct tools optimizing for different phases of the agentic lifecycle. To architect a robust evaluation system for Savant-Code, it is necessary to dissect these existing paradigms, extracting optimal mechanisms while discarding elements that violate the system's operational constraints—specifically, the requirement for a TypeScript strict monorepo, a Windows-first development environment, and the absolute prohibition of secondary in-process language models1.  
The first category of tools focuses on LLM evaluation and generalized assertions. The Inspect AI framework, developed by the UK AI Safety Institute, provides a highly modular architecture that treats evaluations as programmatic compositions of datasets, solvers, and scorers4. While its Python-centric implementation precludes direct adoption within Savant-Code's TypeScript runtime, its conceptual abstraction of separating task definition from the scoring mechanism is highly relevant. OpenBench builds directly upon Inspect AI's primitives to offer provider-agnostic benchmarking across numerous suites, demonstrating the viability of a unified routing layer6. Conversely, promptfoo provides a lightweight, git-diffable YAML configuration approach paired with a command-line interface designed for red-teaming and deterministic assertions7. The promptfoo model aligns closely with Savant-Code's existing v2 YAML schema, offering a pathway to extend the current deterministic checks with structured red-teaming capabilities without requiring heavy containerization.  
The second category encompasses agent and environment harnesses designed for complex software engineering tasks. Terminal-Bench evaluates agents based on final machine state rather than intermediate conversational trajectories, running tasks within sandboxed terminal environments8. Harbor serves as the underlying framework for Terminal-Bench 2.0, providing orchestration for reinforcement learning environments across cloud providers like Modal and Daytona10. While Harbor's ability to run parallel isolated environments is powerful, its deep reliance on Docker and Python runners violates Savant-Code's Windows-first, Bun-native constraints1. SWE-bench remains the industry standard for resolving real-world GitHub issues, utilizing a rigorous patch-based FAIL\_TO\_PASS grading mechanism12. However, significant audits have revealed that a large portion of SWE-bench tests suffer from inherent breakages, necessitating the use of curated subsets like SWE-bench Verified or contamination-resistant alternatives like SWE-rebench12.  
The third category targets skill-specific efficacy and trajectory evaluation. Caliper introduces a highly specialized harness for agent skills, executing a skill multiple times to generate a reliability metric, followed by a baseline run without the skill to report the performance delta15. This isolated, baseline-comparative approach is precisely what Savant-Code requires to validate agent-authored skills1. SkillsBench similarly measures how effectively agents leverage modular skills to perform specialized workflows, utilizing a paired skill lift metric17. Coder Eval takes a complementary approach by measuring skill activation as an independent variable, evaluating whether an agent correctly triggers a target skill within a sandboxed suite using weighted criteria19. For behavioral analysis, LangChain's agentevals and openevals provide mechanisms for trajectory matching, ensuring that the sequence of agent actions conforms to expected patterns21.  
The final category addresses long-horizon execution and structural scale. CodeScaleBench focuses on enterprise-scale, multi-repository tasks, specifically measuring how external retrieval tooling alters agent output compared to local filesystem access23. Its taxonomy of cross-repository navigation, refactoring, and codebase comprehension provides a critical framework for categorizing complex tasks23. SlopCodeBench addresses the phenomenon of code erosion during iterative specification refinement25. It demonstrates that as agents repeatedly extend their own solutions, code quality degrades through increased verbosity and structural erosion—the concentration of complexity into monolithic functions26. This highlights a severe vulnerability in self-improving systems, indicating that pass-rate metrics alone are insufficient without structural safeguards28.

## **Architectural Decision Records**

The rebuilding of the evaluation infrastructure necessitates foundational shifts in how Savant-Code executes, isolates, and grades programmatic tasks. The following Architectural Decision Records (ADRs) establish the engineering directives for the v3 evaluation system, synthesizing the findings from the landscape analysis into concrete methodologies tailored to the ECHO Protocol and the Bun runtime environment.

### **ADR 1: Grading Philosophy and Autorater Mitigation**

The central tension in evaluation design lies between the absolute reliability of deterministic checks and the semantic flexibility of LLM-as-a-judge frameworks. Systems like SWE-bench rely entirely on patch validation and test suite execution, offering unassailable proof of functional correctness12. Conversely, frameworks like Caliper and Inspect AI integrate LLM autoraters to evaluate nuances that static analysis cannot capture, such as the quality of a generated summary or the appropriateness of an agent's reasoning4. Savant-Code’s invariant mandates a deterministic-first approach, prioritizing mechanical verification over probabilistic judgment1.  
The rebuilt evaluation stack will enforce a tripartite, sequential grading pipeline consisting of Deterministic State Verification, Trajectory Compliance, and a Bounded LLM Autorater. The pipeline will immediately halt and register a failure if the deterministic or trajectory stages fail, ensuring that the autorater is never invoked to salvage a mechanically flawed execution. Deterministic State Verification validates the end-state of the workspace, executing compilation steps, language linters, and unit test suites exclusively via Bun's child\_process.execFileSync35. This adapts the philosophy of Terminal-Bench, inspecting the final machine state rather than relying on the agent's self-reported success8. Trajectory Compliance then parses the .savant/traces/ directory to verify adherence to the ECHO protocol laws, ensuring that separation of duties was maintained throughout the execution2.  
The Bounded LLM Autorater is justified exclusively for evaluating qualitative requirements that lack deterministic signatures. This is strictly limited to communicative nuances, such as verifying that the Scribe agent adequately summarized a complex refactoring operation within the LESSONS.md file, or assessing the visual delta of user interface rendering within the holographic command deck1. To prevent the autorater from exhibiting agreeableness bias—a documented phenomenon where LLM judges favor verbose or sycophantic responses—all autorater prompts must utilize a forced-choice, permutation-invariant rubric37. Rather than asking the judge to rate the output on a numerical scale, the prompt must demand categorical extraction, masking the origin of the text to prevent self-enhancement bias37. For example, the prompt structure will mandate: "Output exactly 'A' if the summary identifies the deprecated API, or 'B' if it omits the API." Furthermore, the judge must execute entirely out-of-process, invoking the operator's configured API endpoint, thereby honoring the strict constraint against loading a secondary in-process LLM that could pollute the agent's active context window1.

### **ADR 2: Skill-Efficacy Grading and Probabilistic Verification**

The introduction of the self-improving harness fundamentally alters the evaluation requirements. Agents now author programmatic skills dynamically, storing these SKILL.md artifacts in a quarantined state within .agents/skills/.quarantine/1. Before an operator can elevate a skill to a trusted status, the system must provide empirical proof that the skill genuinely improves agent performance1. The methodology established by Caliper—running multiple trials against a task with the skill active, followed by a baseline re-run without the skill to report the performance delta—provides the ideal architectural foundation for this verification15.  
The system will implement a native skills prove \<name\> capability, leveraging a dual-metric statistical evaluation engine grounded in Anthropic’s engineering models for evaluating non-deterministic agents38. The evaluation runner will execute ![][image1] independent, isolated sandbox trials of a specific task without the skill loaded to establish the Baseline15. Subsequently, it will execute ![][image1] trials of the exact same task with the target skill actively injected into the tool registry to establish the Skill-Active state31. The mathematical efficacy delta is defined as the paired skill lift: the expected score of the skill-active runs minus the expected score of the baseline runs18.  
Crucially, the evaluation will distinguish between capability and reliability by reporting both ![][image2] and ![][image3] metrics38. The ![][image2] metric calculates the probability that the agent succeeds at least once in ![][image1] attempts, modeled as ![][image4] where ![][image5] is the per-trial success rate39. This metric measures raw capability, determining whether the skill enables the agent to solve a problem it previously found impossible40. A positive ![][image2] lift is the minimum threshold for a quarantined skill to be presented to the operator for review.  
Conversely, the ![][image3] metric calculates the probability that all ![][image1] attempts succeed consecutively, modeled simply as ![][image6]39. This metric measures strict reliability and operational consistency41. An agent with a 75 percent single-trial success rate will achieve a ![][image7] score of only roughly 42 percent, illustrating how rapidly reliability degrades across repeated executions38. The ![][image3] reliability score, alongside the cryptographic hashes of the ![][image1] successful execution traces, must be inextricably bound to the Zero-Trust Agentic Provenance (ZTAP) receipt generated upon operator approval3. The framework will enforce a strict governance gate: a skill cannot be promoted to the immutable: true status without achieving a ![][image3] score exceeding 0.95 across a minimum of ![][image8] trials, ensuring that only statistically proven behaviors solidify into the permanent architecture1.

### **ADR 3: End-State Verification and Bun-Native Sandboxing**

Evaluation harnesses like Terminal-Bench and Harbor rely heavily on Docker or remote cloud environments (such as Modal or Daytona) to isolate task execution and inspect final machine states8. While highly secure, this containerized dependency fundamentally conflicts with Savant-Code’s developer reality, which mandates a Windows-first, Docker-less execution environment that minimizes computational overhead and setup friction1. The v3 evaluation system must replace the legacy Linux-only Docker stub with a robust, Bun-native ephemeral workspace model capable of running securely on Windows.  
The implementation will utilize Bun's highly optimized node:fs capabilities to rapidly clone complex repository fixtures directly into virtualized temporary directories provided by os.tmpdir()43. On Windows systems, this process will leverage native NTFS junction points and optimized file system calls to instantiate the isolated sandbox in milliseconds without the virtualization tax of a container1. The deterministic end-state verification scripts will execute directly against this temporary directory context, asserting the presence of required files, the absence of prohibited patterns, and the successful execution of language-specific toolchains8.  
Process isolation in a Docker-less environment requires strict management of sub-processes to prevent runaway agent loops from consuming host resources or leaving orphaned executables. The evaluation runner will implement native operating system primitives to enforce isolation. On Linux, the runner will utilize prctl(PR\_SET\_PDEATHSIG, SIGKILL) to ensure that all spawned subagents, bash processes, and background servers terminate instantaneously if the primary evaluation runner aborts or crashes43. On Windows, equivalent process grouping will be enforced utilizing Job Objects, guaranteeing clean teardown of the ephemeral workspace43.  
A critical technical consideration is the handling of standard output from these isolated processes. The Bun runtime exhibits a known constraint where standard output streams piped from child\_process.execFileSync on certain platforms truncate exactly at 8,192 bytes due to libc buffering behaviors inherited from underlying C/C++ implementations36. Because evaluation traces and linter outputs frequently exceed this 8KB threshold, the evaluation runner must meticulously avoid synchronous buffer reads. Instead, the runner will execute sandboxed tasks utilizing asynchronous streaming via Bun.spawn, piping output directly to temporary log files on disk before executing validation assertions against those files, thereby entirely bypassing the truncation vulnerability36.

### **ADR 4: Task Corpus Strategy and Governance Verification**

The existing v2 benchmark relies on a limited array of manually curated YAML tasks categorized broadly into pure coding and error recovery scenarios1. To adequately evaluate a complex, multi-agent governed system, the corpus strategy must evolve to resist dataset contamination while comprehensively measuring both software engineering capability and strict protocol compliance.  
To combat contamination—the phenomenon where models memorize public benchmark solutions during pre-training—the capability task corpus will implement an automated ingestion pipeline inspired by the SWE-rebench methodology12. This pipeline will dynamically pull closed, time-windowed issues from the operator's own proprietary repository history or specifically targeted, recently updated open-source repositories14. The ingestion engine will classify these tasks by adapting the CodeScaleBench taxonomy, stratifying the corpus into cross-repository navigation, dependency tracing, codebase comprehension, and security remediation tasks23. This ensures that the evaluation measures genuine problem-solving ability across enterprise-scale architectures rather than memorized snippets23.  
Equally critical is the introduction of a proprietary suite of Governance Tasks designed exclusively to verify adherence to the ECHO Protocol1. While capability tasks measure what the agent *can* do, governance tasks measure what the agent *refuses* to do. This corpus will include Role-Boundary Refusal tasks, which prompt specialized agents like the Verifier to execute write commands, expecting a definitive refusal due to separation of duties2. It will incorporate Law 1 Traps to enforce the "Read 0-EOF" mandate, supplying a massive source file with a hidden instruction embedded near the end to prove the agent did not skip reading the full context2. Furthermore, Adversarial Override simulations will inject false-positive audit findings into the context to ensure the Adversary agent correctly refutes the claim and cites the precise file and line number, preventing hallucinated errors from stalling the Perfection Loop2.

### **ADR 5: FSM-Compliance Scoring**

The v2 evaluation framework scores phase compliance through relatively rudimentary parsing of execution traces1. However, a governed multi-agent system requires behavioral metrics that rigorously distinguish an ECHO-compliant execution from an unconstrained, raw LLM loop1. FSM-compliance scoring must evolve into an exact Trajectory Match engine, adapting the conceptual rigor of LangChain's agentevals and openevals to validate the sequence and legality of agent actions21.  
The Trajectory Match engine will perform deterministic assertions against the append-only ZTAP session ledger generated during execution3. The primary metric is State Transition Legality, which validates that the Orchestrator invokes the transition\_phase tool strictly in accordance with the permissible paths of the Perfection Loop finite state machine: idle leading to red, advancing to green, proceeding to audit, escalating to adversarial, and finally reaching complete2. Any deviation from this directed graph, such as transitioning directly from green to complete without undergoing an audit phase, will trigger an immediate evaluation failure2.  
Beyond state transitions, the engine will enforce Separation of Duties checks. By analyzing the toolNames arrays within the execution traces, the evaluator will mathematically prove that the Forge agent's trace excludes the bash tool, ensuring it never verified its own implementation, and that the Verifier's trace completely excludes write\_file and str\_replace tools2. Finally, the engine will track Thinker Convergence2. It will analyze the sequential thinking tool usage, ensuring that the nextThoughtNeeded: false flag was genuinely emitted before any phase transition occurred, and grading the depth of branchFromThought exploration to confirm that alternative architectural approaches were considered before code was written2.

### **ADR 6: Self-Improvement Regression Guard**

The introduction of the self-improving harness enables the system to mechanically capture tool failures, extract recurring patterns, and draft new skills into quarantine1. However, long-horizon iterative tasks present a severe risk of architectural decay. The SlopCodeBench research demonstrates that as agents repeatedly extend their own previous solutions across multiple checkpoints, code quality degrades systematically, even if functional pass rates remain stable25. This degradation manifests as code erosion and verbosity bloat, turning maintainable codebases into unmanageable artifacts28.  
To protect the Savant-Code repository from this phenomenon, the evaluation system will integrate a SlopCodeBench-style Regression Guard embedded directly into the skills:evolve pipeline and the CI release gates1. When the Scribe agent proposes the promotion of a drafted skill, the evaluation runner will execute a multi-turn extension task designed to force architectural decisions26. The grading script will subsequently parse the abstract syntax tree (AST) of the generated code utilizing the internal @savant-code/code-map tree-sitter index3.  
The Regression Guard will measure two specific trajectory-level signals. First, it will calculate the Verbosity Delta, defined as the ratio of tokens generated to the actual functional complexity added, identifying instances where the agent favors redundant, duplicated logic over clean abstraction26. Second, it will measure Structural Erosion, calculating the cyclomatic complexity and cross-module coupling to detect the concentration of complexity mass into monolithic "god-functions"26. If the application of a new skill increases structural erosion beyond a rigid 5 percent threshold compared to the baseline execution, or if it noticeably degrades the ![][image3] reliability metric, the ECHO Harness Enforcement Layer (EHEL) will permanently block the skill's promotion2. This ensures that the Perfection Loop optimizes for multi-year maintainability (ECHO Law 13\) rather than mere immediate task completion2.

### **ADR 7: Cost and Continuous Integration Constraints**

Agentic evaluations are inherently resource-intensive, consuming vast amounts of tokens and wall-clock time. Integrating these evaluations into a development workflow requires respecting the operator's budget constraints and the existing pre-push release gate structure1. A monolithic evaluation suite that runs on every commit is financially and temporally unviable.  
The architecture will establish a three-tier execution strategy based on computational cost and statistical necessity, providing escalating levels of assurance.

* **Tier 1: Pre-Commit (Smoke)**: This tier executes deterministically on every git push invocation1. It runs 5 critical Governance Tasks focused entirely on prompt-rejection, ECHO Law 1 adherence, and FSM transition legality2. To achieve a zero-token API cost, this tier utilizes mocked LLM responses or highly quantized local Ollama models3. The execution time budget is strictly capped at under 30 seconds.  
* **Tier 2: Nightly (Regression)**: Triggered via scheduled continuous integration, this tier evaluates the ![][image3] consistency of all currently active immutable: true skills against a curated suite of 50 tasks1. It operates using the operator's primary configured LLM (e.g., OpenRouter openrouter/free or a paid tier)3. The token expenditure is estimated at roughly 200,000 tokens (50 tasks ![][image9] 4,000 tokens per trace), with a time budget under 15 minutes.  
* **Tier 3: Release (Capability and Erosion)**: This exhaustive tier is triggered exclusively via the release:public command prior to a version bump3. It executes the full CodeScaleBench and SWE-rebench ingestion corpus, testing maximum ![][image2] capability alongside the long-horizon SlopCodeBench structural erosion metrics23. This tier requires substantial compute, estimated at upwards of 2,000,000 tokens, serving as the final definitive gate before software distribution.

### **ADR 8: License Compliance**

Savant-Code is distributed under the Apache-2.0 license, making strict legal compatibility a non-negotiable requirement for the evaluation framework1. The landscape analysis confirms that the primary mechanisms targeted for adaptation derive from projects with highly permissive licenses. Code ported or adapted from Caliper, Inspect AI, promptfoo, Coder Eval, SWE-bench, and SlopCodeBench operates under the MIT License5. Frameworks such as Terminal-Bench, Harbor, SkillsBench, and CodeScaleBench operate under the Apache-2.0 License10.  
These MIT and Apache-2.0 sources are fully compatible with Savant-Code’s licensing constraints. The integration of their methodologies—such as Caliper's YAML parsing logic, SlopCodeBench's tree-sitter erosion calculations, or Coder Eval's activation precision checks—can proceed without legal friction15. Any framework or snippet surfaced bearing copyleft licenses (e.g., GPL, AGPL) or proprietary restrictions must be strictly rejected to prevent viral contamination of the monorepo1. All adapted logic will carry precise attribution in the repository's NOTICE file, ensuring complete compliance while leveraging the vanguard of open-source evaluation research.

## **Phased Rebuild Plan**

Migrating from the functional but limited benchmark v2 to the comprehensive v3 architecture requires a staged, incremental rollout. Each phase is designed to be independently shippable, preserving backward compatibility with existing YAML tasks via bridging adapters to prevent disruption to ongoing development.  
**Phase 1: Bun-Native Isolation and ZTAP Integration** The initial phase focuses on stripping the Linux-only Docker dependency and establishing the Windows-first sandboxing model1. The engineering team will implement the SandboxManager leveraging Bun's fs.mkdtemp to virtualize execution within ephemeral directories44. The legacy v2 tasks will be mounted into this new file system structure. The AgentRunner interface and the existing v2 task registry will survive this phase entirely intact1. Verification will require confirming that process isolation utilizing Job Objects successfully cleans up spawned processes on Windows, and that asynchronous streaming mitigates the known child\_process 8KB truncation bug36.  
**Phase 2: Skill-Efficacy Engine and CLI Integration** The second phase introduces the statistical mechanisms necessary to evaluate agent-authored skills. The team will build the skills prove \<name\> CLI command, implementing the ![][image1]\-trials execution loop to generate baseline and skill-active performance deltas15. This phase will adapt the skill\_triggered activation assertion logic from Coder Eval to verify that the agent actually utilizes the skill being tested19. Successful validation of this phase requires the end-to-end execution of a quarantined skill demonstrating a positive ![][image2] capability lift, culminating in the generation of a signed ZTAP receipt3.  
**Phase 3: Exact FSM and Governance Verification** The third phase replaces the loose trace scoring engine of v2 with the rigorous Trajectory Match engine1. Deterministic validators for the ECHO Protocol v0.2.0 laws will be constructed2. The system will enforce the sequential progression of the Perfection Loop (idle ![][image10] complete) and mathematically assert that specific tools were excluded from specialized agents2. The existing v2 schema will survive but will be heavily augmented with a new trajectory\_assertions array to support these strict checks.  
**Phase 4: SlopCodeBench Regression Guard and End-State Grading** The fourth phase secures the self-improving harness against architectural decay1. The @savant-code/code-map package will be integrated into the evaluation runner to measure cyclomatic complexity and verbosity ratios before and after task execution3. Simultaneously, Terminal-Bench's final machine state inspection philosophy will be adapted to validate complex multi-file edits deterministically without relying on Docker8. This phase ensures that the long-term maintainability of the codebase is mathematically protected.  
**Phase 5: External Capability Ingestion** The final phase expands the evaluation corpus to resist contamination and increase complexity. Parsers will be built to ingest the CodeScaleBench taxonomy and the SWE-rebench live-issue formats14. These external tasks will be converted dynamically into the extended v3 YAML schema. The Tier 3 (Release) CI pipeline will be deployed to execute these massive suites, bringing the full weight of the new evaluation architecture to bear on final release candidates.

## **Risk Register**

The implementation of this blueprint carries specific technical and operational risks that must be actively managed during the rebuild process.  
First, the reliance on Bun's child\_process for deterministic state verification on Windows exposes the system to the aforementioned 8,192-byte stdout truncation bug36. If the evaluation runner relies on synchronous buffer reads, large test suite outputs will be silently truncated, leading to false-negative evaluations. Mitigation requires strict adherence to asynchronous Bun.spawn streaming and piping outputs to temporary disk files before evaluation36.  
Second, executing arbitrary code generated by the agent within temporary directories on a Windows host—rather than within a hardened Docker container—presents a sandbox escape vulnerability1. An agent hallucinating destructive commands (e.g., rm \-rf / equivalents) could damage the operator's machine. Mitigation requires the evaluation runner to forcefully inject permission-mode: safe into the execution context, physically stripping destructive shell capabilities at the tool-executor.ts boundary before the agent can invoke them3.  
Third, the unbounded execution of ![][image1]\-trials during skill-efficacy grading can rapidly exhaust the operator's configured LLM API budget1. Mitigation involves enforcing hard token ceilings within protocol.config.yaml and defaulting the ![][image1] variable to 3 for local interactive tests, reserving the statistically robust ![][image11] executions strictly for automated CI pipelines where budgets are centrally managed1.  
Finally, the Bounded LLM Autorater remains susceptible to agreeableness bias, potentially approving verbose but factually incorrect Scribe summaries37. Mitigation demands the strict prohibition of open-ended grading prompts, mandating the use of permutation-invariant, forced-choice rubrics for all model-graded evaluations.

## **Honest Boundaries**

It is imperative to define the epistemic limits of this evaluation architecture. The metrics generated by the ![][image3] capability and reliability engines, as well as the ZTAP provenance receipts, provide cryptographically signed evidence of *mechanical process adherence*, not definitive proof of LLM cognitive independence3. If an underlying foundation model has memorized a specific benchmark solution during pre-training, the evaluation framework cannot inherently detect this data contamination. Operators must continuously rotate the capability tasks utilized in Tier 3 evaluations to ensure the validity of the generated scores.  
Furthermore, any evaluation phase utilizing the LLM autorater, however tightly bounded, introduces inherent stochasticity into the grading process. Benchmark numbers for qualitative tasks must always be reported as statistical distributions across trials, never as absolute factual guarantees. Similarly, the structural erosion metrics derived from SlopCodeBench methodologies rely on static analysis via tree-sitter AST parsing3. These measurements represent heuristic approximations of technical debt and verbosity, not infallible architectural judgments26. They provide directional vectors for code quality, but ultimately, human operator verification remains the final arbiter of system integrity.
