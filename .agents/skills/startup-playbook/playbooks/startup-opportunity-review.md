# Startup Opportunity Review Playbook

## When to use

Use this playbook to review a real AI startup or current product direction. Before starting, gather facts about users, technology, costs, competition, and the team. If only an idea exists, label it explicitly as a hypothesis.

## Prerequisites

- The user provides the project's goal and current state.
- The reviewer can distinguish speaker claims in the source from evidence observed in the project.
- The user is willing to define observable signals that would change the judgment.

## Procedure

1. **Establish evidence of a shift:** List project facts showing what has actually changed in technology speed, cost, iteration cycles, or incumbent advantage. Where no fact exists, retain the claim as a hypothesis to test. `claim-apply-opportunity-1`
2. **Reassess the problem ceiling:** State what capability AI leverage releases and what larger mission it allows the team to pursue. Remove any inconsistent exact multiplier taken from the video. `claim-apply-opportunity-2`
3. **Restore business fundamentals:** Review user value, taste, agency, business physics, and moat separately so that tool fluency does not become the entire advantage. `claim-apply-opportunity-3`
4. **Write a falsifiable non-consensus hypothesis:** Record evidence that would strengthen, weaken, and overturn the belief. Concrete thresholds are inferences for the current project, not claims from the video. `claim-apply-opportunity-4`
5. **Check the small group of shared believers and relationship compounding:** Find a few people who genuinely understand the hypothesis and choose one real act of help that does not depend on an immediate return. Do not freeze the video's location advice in time. `claim-apply-opportunity-5`
6. **Choose a data-generating step:** When the full path remains unclear, choose an imperfect action that will create new information and define the observable states before and after it. `claim-apply-opportunity-6`

## Expected state

A one-page review containing the shift facts, new problem ceiling, unresolved fundamentals, falsifiable hypothesis, relationship strategy, next action, and observed result.

## Validation

- Label every judgment as at least one of "source claim," "project fact," or "inference."
- Include at least one signal that would weaken the current belief.
- Make the result of the next action observable so that even failure can update the judgment.

## Recovery

- If there are no shift facts, return to user interviews, cost measurements, or technical probes instead of declaring that a window exists.
- If there are no shared believers, inspect the quality of the explanation and the hypothesis itself instead of immediately treating isolation as proof.
- If everyone agrees, check whether the project lacks a non-consensus advantage or has entered a crowded direction.
- If the step generates no data, reduce its scope until a before-and-after state can be defined.

## Limitations

The video provides no universal thresholds, uniform iteration cadence, or market-validation method. These must be inferred and tested in the current project.
