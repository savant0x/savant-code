## Summary

The v0.0.35 public release published to npm and created its GitHub release, but the
`Build and Publish Release Binaries` workflow failed on all five platforms at the
`Build binary` step, so the release carries **zero** binary assets. `packages/connectors`
imports `ajv/dist/2020.js` and `ajv-formats` without declaring either in its
`package.json`; both resolved locally only from stale ajv v8 files left inside a
root `node_modules/ajv` that otherwise holds ajv **v6**. Every local release gate ran
green against that contaminated install, and the failure first surfaced in CI — after
npm had already published. This is the `FID-2026-0816-001` (v0.0.24) incident class
recurring with a different resolution mechanism.

- **OS:** Windows 11

## Detailed Description

### Problem

Two user-visible symptoms, one cause:

1. The GitHub release `v0.0.35` has no assets at all. `gh release view v0.0.35 --json assets`
   returns an empty list, while `v0.0.34` carries all five tarballs.
2. Existing CLI installs do not auto-update. The npm `savant-code` package is a thin
   launcher: `getLatestVersion()` reads the **npm** registry latest (`0.0.35` is published),
   then `downloadBinary()` fetches
   `releases/download/v0.0.35/savant-code-<target>.tar.gz`, which 404s. The staging
   failure is swallowed by design (`cli/release-core/launcher.js` `checkForUpdates`
   catch — "A staging failure leaves the current process and binary untouched"), so the
   launcher silently keeps the stale binary instead of reporting anything.

### Expected Behavior

The build workflow uploads all five tarballs to the release, so the published npm
version serves a downloadable binary and consent-gated auto-update proceeds normally.
A source import must resolve from the repository's own declared dependencies, not from
a stale or out-of-repo `node_modules`.

### Root Cause

`packages/connectors/src/engine/validate.ts:1-2` imports `ajv/dist/2020.js` and
`ajv-formats`, but `packages/connectors/package.json` declares only `canonicalize` and
`zod`.

`ajv` is therefore a **phantom dependency**. In the lockfile, ajv v8 exists only as a
nested resolution under `ajv-formats` (key `ajv-formats/ajv`), while the top-level,
hoistable `ajv` entry is **6.15.0** (pulled in by eslint). Upstream ajv 6 ships no
`dist/2020.js` — that entry point is an ajv v8 API — so a clean checkout has nothing
for `packages/connectors` to resolve.

Locally the import works by accident: `C:\Users\spenc\dev\savant-code\node_modules\ajv`
reports version `6.15.0` yet contains a full v8 `dist/` tree (`2020.js`, `2019.js`,
`jtd.js`, `vocabularies/`, `standalone/`). Stale v8 files survived a later install that
hoisted ajv v6 into the same folder. Bun does not prune them, so `bun build` resolved
`ajv/dist/2020.js` against a directory that is half v6 and half v8.

This is why the whole local battery passed — including `cli-bundle-resolution`, the gate
added specifically for the phantom class by `FID-2026-0816-001` G-03. That gate is
structurally correct but executes `bun build` against the *local* `node_modules`, so a
contaminated install defeats it. The v0.0.24 variant resolved from a `node_modules`
outside the repo; this one resolves from a mutated `node_modules` inside it.

## Proposed Solution

### Approach

Declare the dependency the code already uses, so the import resolves from the repository's
own manifest rather than from a stale hoist. Then backfill the five tarballs onto the
existing `v0.0.35` release from a branch/tag ref, per the documented remediation flow in
`docs/public-release.md` (§ "Release incident: v0.0.24"). No version bump: the npm
launcher serves whichever release its version points at, so once the binaries exist the
published `0.0.35` works.

### Steps

1. Add `ajv` (`^8.17.1`) and `ajv-formats` (`^3.0.1`) to `packages/connectors/package.json`
   `dependencies` — `implemented`.
2. Sweep every bare import specifier in `packages/connectors/src` (the ADVERSARIAL check)
   and fix the one further undeclared dependency it found: `@savant-code/common/util/hash`

4. Verify the resolution no longer rides the contaminated root, and that the CI-equivalent
   `bun build --compile` succeeds for a real target — `implemented`.
5. Push the fix to `main` and dispatch `build-release-binaries.yml` with

## Lessons Learned

A gate that resolves imports from the developer's `node_modules` cannot prove that a
clean checkout resolves them. The `FID-2026-0816-001` guard was written against a
phantom *outside* the repo and is blind to a mutated install *inside* it — a stale
directory surviving an install reproduces exactly the same false green. Durable fix is
to assert the *manifest*, not the resolution.
