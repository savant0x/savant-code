## Summary

Phase 1 of the Tool Safety + Sandbox Engine has been implemented and audited. The agent runtime now evaluates every tool call against a declarative safety policy before the handler runs. The policy layer blocks destructive shell commands, gates network access, and enforces a user-selected permission mode (`safe`/`prompt`/`unsafe`) without changing git or worktree workflows.

## What Changed

### New files

- `common/src/tools/safety.ts`
  - `ToolEffect`, `ToolPermission`, `SandboxPermissionMode`, `SandboxPolicy`, `SandboxDecision` types.
  - Clean, minimal public surface for Phase 1.

## Scope Confirmation

- **Included in Phase 1:**
  - Declarative safety metadata per tool.
  - Sandbox policy evaluation (safe/prompt/unsafe).
  - Destructive shell command denylist.
  - Network gate.
  - `permissionMode` propagation via SDK + CLI state.
  - `devMode` bypass with warning.

- **Deliberately out of scope (future FIDs):**
  - OS-level sandboxing (landlock/seccomp/seatbelt).
  - Secrets redaction.
  - Persistent grant store.
  - Interactive TUI permission modal (prompts currently downgrade to deny in headless mode).
  - Plugin/MCP custom safety metadata (unknown tools default to `mixed`/`prompt`).
