# 2026-10-11 — v0.0.35 shipped without binaries: phantom `ajv` in `packages/connectors`

**Session type:** incident response (release repair)
**Trigger:** operator report — the v0.0.35 release page has missing binaries and the CLI
stopped auto-updating on launch.
**FID:** `FID-2026-1011-003` (closed, archived)
**Autonomy:** Level 3 session ceiling; the two external mutations (push, workflow
dispatch) were separately authorized by the operator before execution.

## What happened

The `v0.0.35` public release published to npm (`0.0.35` is live and remains the npm
`latest`) and its GitHub release was created, but the release carries **zero** assets.
The `Build and Publish Release Binaries` workflow (run `38175849791`, triggered by
`on: release: types: [published]`) failed on **all five** platforms at the `Build
binary` step:

```text
error: Could not resolve: "ajv/dist/2020.js". Maybe you need to "bun install"?
    at .../packages/connectors/src/engine/validate.ts:1:21
```

Both user-visible symptoms have this one cause. The npm `savant-code` package is a thin
launcher: `getLatestVersion()` reads the npm registry (`0.0.35`), then downloads
`releases/download/v0.0.35/savant-code-<target>.tar.gz`, which 404'd. The staging
failure is swallowed by design (`checkForUpdates` catch — "A staging failure leaves the
current process and binary untouched"), so every existing install silently stayed on its
old binary instead of reporting anything.

The pipeline's own `verifyReleaseAssets` poll then ran its full 45-minute retry window
before failing, which is why the release looked "failed on the very last step" — by then
`GITHUB_RELEASE` and `NPM_PUBLISH_CLI` had already completed 45 minutes earlier.

## Root cause

`packages/connectors/src/engine/validate.ts:1-2` imports `ajv/dist/2020.js` and
`ajv-formats`, but `packages/connectors/package.json` declared neither — a **phantom
dependency**.

In the lockfile the only hoistable `ajv` was **6.15.0** (pulled in by eslint); ajv v8
existed solely as a nested resolution under `ajv-formats` (lock key `ajv-formats/ajv`).
Upstream ajv 6 ships no `dist/2020.js` — that entry point is an ajv v8 API — so a clean
checkout had nothing for the package to resolve.

Locally the import worked by accident: `node_modules/ajv` reported version `6.15.0` yet
contained a full v8 `dist/` tree (`2020.js`, `2019.js`, `jtd.js`, `vocabularies/`,
`standalone/`) left behind by an earlier install. Bun does not prune stale files, so
`bun build` resolved against a directory that was half v6 and half v8.

This is why the entire local gate battery passed — **including `cli-bundle-resolution`**,
the gate `FID-2026-0816-001` G-03 added specifically for this class. That gate is
structurally sound but executes against the *local* `node_modules`, so a contaminated
install defeats it. The v0.0.24 incident resolved from a `node_modules` **outside** the
repo; this one resolved from a mutated `node_modules` **inside** it. The guard was blind
to the new variant.

## Fix

Committed as `4d2369bd` (`fix(connectors): declare phantom ajv and common deps`):

- `packages/connectors/package.json` — declared `ajv ^8.17.1`, `ajv-formats ^3.0.1`.
- The FID's own import sweep then found a second undeclared dependency of the same class
  in the same package — `@savant-code/common/util/hash` at
  `packages/connectors/src/core/schema/json/stable-stringify.ts:8` — so
  `@savant-code/common` (`workspace:*`) was declared alongside it, matching the
  convention `desktop`, `evals`, `packages/knowledge-graph`, and `packages/llm-providers`
  already follow. This was hygiene, not a release blocker: the workspace link makes it
  resolvable in any install.
- `bun.lock` regenerated via `bun install`: ajv hoists to `8.20.0` and eslint's ajv 6
  nests correctly under `eslint/ajv` and `@eslint/eslintrc/ajv`.

## Residual — not dropped

`T188` (registered in `SCOPE.md`, blocked): `cli-bundle-resolution` cannot catch this
class because it resolves from whatever `node_modules` the machine happens to have. An
**install-independent** manifest-vs-import sweep — asserting each workspace's bare
specifiers against its own declared dependencies — would catch it without trusting the
installed tree. It is not landed unilaterally because joining the fail-closed release
gate battery is an operator ruling (the T186 precedent).

Also noted, unchanged and unrelated: `desktopStagesSkipped: true` on the original release
(`SAVANT_CODE_RELEASE_DESKTOP` unset) was expected behaviour, and the release receipt's
`failedStage` remains on disk as the historical record of the failed run.
