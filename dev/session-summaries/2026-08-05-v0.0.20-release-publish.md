## Version-bump rationale (0.0.19 → 0.0.20)

- **`npmjs.com` showed `0.0.18` as latest — but the registry had a stale
  `0.0.19` already published** (2026-08-04T14:49Z, *before* the 0.0.18 hotfix
  publish at 15:53Z which became `latest`). The stale 0.0.19 tarball was a
  launcher package whose binary download pointed at a **v0.0.19 GitHub release
  that never existed** — a broken publish.
- npm refuses to republish an existing version string, so shipping the current
  tree as 0.0.19 was impossible without unpublishing. Operator chose **ship as
  0.0.20** (clean, no registry surgery).
- Bumped: `VERSION`, root/cli/release/sdk `package.json`, `protocol.config.yaml`,
  README + zh-CN badges and intro lines, CHANGELOG head (`## v0.0.20 — 2026-08-05`)
  with a version-note explaining the relabel. Historical `0.0.19` references in
  `docs/`, archived FIDs, and session summaries were left untouched as records.

## Operational notes / near-misses

- **`.env.local` restore hiccup:** the clean-shell build command's output was
  truncated mid-run and the `mv` restore never executed — `.env.local` was
  missing afterward. Restored from the `/tmp` backup in a follow-up command.
  Lesson: treat build-shell env hygiene as two independent steps (unset +
  move-aside) and verify the restore explicitly, not just from the command tail.
- **Windows native curl cannot read `/tmp/` paths** (Git-bash path mapping):
  the release-body JSON had to be written into the repo working tree and posted
  with `-d @./release-body-tmp.json`, then deleted.
- **Pre-publish collision check caught the whole problem:** checking
  `npm view savant-code versions --json` + raw registry metadata
  (`curl https://registry.npmjs.org/savant-code`) before publishing revealed the
  stale 0.0.19; `dist-tags.latest` alone (0.0.18) was not the full story.
- npm launcher package remains a binary downloader (`files: index.js, launcher.js,
  http.js, README.md`); the 5 native binaries ship only via the GitHub release
  assets, which the Actions workflow uploads.
